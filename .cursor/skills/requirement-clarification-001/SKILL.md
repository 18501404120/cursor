# 需求澄清001

## 何时使用

- 用户说「需求澄清001」「需求澄清 001」「做需求澄清」「澄清当前需求」「检查需求不明确点」等。
- 用户要求从**开发、测试、用户**视角审读需求文档、PRD、方案说明或 HTML 原型。
- 用户希望把疑问点、不明确点、建议补充逻辑、**建议方案**、建议验收标准整理成表格。

## 核心原则

- 默认只在**聊天中输出澄清表**，不新建或修改文件；只有用户明确要求保存时才写入文件。
- 默认固定使用 **开发视角、测试视角、用户视角**；若用户提示词明确指定某一种或某几种视角，则按提示词执行。
- 必须检查**需求文档与原型的一致性**：若同一任务同时存在文档和原型，逐项对照页面、字段、筛选、按钮、流程、状态和异常；若只提供其中之一，说明跨源一致性无法完整检查，并将缺少对照材料列为风险或待确认项。
- 每条澄清点必须包含「疑问点」「建议补充逻辑」和「建议方案」，避免只提出泛泛问题。
- **建议补充逻辑**写「要补什么」；**建议方案**写「怎么补、补成什么样」的完整可评审方案。
- 优先级使用 **高 / 中 / 低**。

## 执行步骤

1. **确定输入来源**
   - 若用户给出文件或文件夹路径：读取相关需求文档、说明文档、HTML 原型及同目录明显相关文件。
   - 若用户粘贴内容：以粘贴内容为输入。
   - 若用户说「当前需求」「当前原型」但路径不明确：优先使用当前打开或最近查看的需求/原型文件；仍不明确时只问一次路径。

2. **识别审读视角**
   - 默认：开发、测试、用户三种视角都检查。
   - 若用户明确说「只从测试视角」「开发视角」等：仅输出指定视角。

3. **结构化提取需求**
   - 提取模块/页面、入口、角色、字段、筛选项、按钮、表格列、弹窗、状态、权限、业务规则、计算公式、数据来源、异常处理、验收描述。
   - 对 HTML 原型重点查看页面结构、可见控件、交互脚本、mock 数据、提示文案和隐藏状态。

4. **三视角检查**
   - **开发视角**：数据来源、字段口径、接口边界、状态流转、权限、计算规则、幂等/重复提交、历史数据兼容、异常分支。
   - **测试视角**：验收标准、边界值、必填校验、组合条件、空数据、重复数据、超限、失败提示、回归影响。
   - **用户视角**：入口是否清晰、操作路径是否顺、文案是否可理解、结果是否可解释、反馈是否明确、是否缺少确认或撤销。

5. **强制一致性检查**
   - 文档有但原型没有：列为「原型缺失/不一致」。
   - 原型有但文档没有：列为「文档缺失/不一致」。
   - 字段命名、筛选范围、按钮行为、默认值、状态文案、异常提示不一致：逐条列出。
   - 若无法判断谁是准绳，在「建议补充逻辑」与「建议方案」中写明需产品确认的分支及推荐默认选项。

6. **输出澄清表**
   - 默认按优先级从高到低排序，同优先级按业务流程顺序排序。
   - 输出表格后，用 2-4 句话补充「主要风险」和「建议下一步」。

## 澄清点类型

| 类型 | 判定口径 |
|------|----------|
| 业务规则缺失 | 只有目标，没有规则、条件、状态或处理分支 |
| 字段定义不清 | 字段含义、格式、来源、枚举、精度、默认值不明确 |
| 交互状态不明 | 点击、保存、提交、撤销、刷新、失败后的页面状态不明确 |
| 权限边界不明 | 哪些角色可见、可操作、可审批、可导出不明确 |
| 数据口径不清 | 统计范围、时间口径、快照/实时、币种、汇率、维度关系不明确 |
| 异常处理缺失 | 空数据、重复、超限、接口失败、并发、历史数据未说明 |
| 验收标准缺失 | 无法直接转成测试用例或判断是否通过 |
| 文档原型不一致 | 需求文档与原型在页面、字段、流程、文案或行为上不一致 |

## 输出格式

使用 Markdown 表格，**「建议方案」列紧接在「建议补充逻辑」之后**：

| 编号 | 模块/页面 | 角色视角 | 疑问点 | 不明确类型 | 影响说明 | 建议补充逻辑 | 建议方案 | 建议验收标准 | 需确认对象 | 优先级 | 状态 |
|------|-----------|----------|--------|------------|----------|--------------|----------|----------------|------------|--------|------|
| Q-001 | 示例页面 | 开发视角 | 示例疑问 | 业务规则缺失 | 说明不澄清会造成的开发/测试/使用影响 | 简要说明需补充的规则方向（1～2 句） | **完整建议方案**（见下方结构要求） | 给出可执行、可验证的通过标准 | 产品/业务/开发/测试 | 高 | 待确认 |

### 「建议方案」列写法（必须完整、可评审）

每条「建议方案」须自成一体，建议按以下结构组织（可用分号或编号，不必每项都写全，但须覆盖决策结论）：

1. **推荐结论**：明确采纳的方案（一句话定调）。
2. **业务规则**：条件、分支、默认值、计算公式或状态机。
3. **数据/接口**：字段来源、主键、同步频率、快照策略（如适用）。
4. **界面/交互**：页面改什么、按钮/文案/校验（如适用）。
5. **异常与边界**：失败提示、回滚、幂等、历史数据处理（如适用）。
6. **待产品确认项**（可选）：若存在多方案，写明推荐项及备选。

「建议补充逻辑」与「建议方案」的分工：

- **建议补充逻辑**：指出缺口与补充方向，偏「问题定义」。
- **建议方案**：给出可直接进入评审/排期的完整方案，偏「问题解法」。

## 优先级定义

- **高**：不澄清会阻塞开发、测试或验收；可能导致数据错误、权限风险、核心流程不可用。
- **中**：不阻塞主流程，但会造成实现差异、测试遗漏、用户误解或返工风险。
- **低**：主要影响文案、提示、易用性、展示一致性，建议补充但不影响核心逻辑。

## 输出要求

- 「疑问点」写成具体问题，不写空泛判断。
- 「建议补充逻辑」必须给出可落地的补充方向，尽量包含条件、分支、默认值、数据口径或示例。
- 「建议方案」必须给出**完整、可评审、可拆分任务**的方案描述；禁止只重复「建议补充逻辑」的措辞。
- 「建议验收标准」必须可测试，例如“当 X 条件发生时，页面应展示 Y，并禁止 Z 操作”。
- 不直接替用户改写需求正文，除非用户明确要求。
- 若输入信息不足，先输出基于现有材料的澄清表，再列出缺失材料，不要反复追问。
