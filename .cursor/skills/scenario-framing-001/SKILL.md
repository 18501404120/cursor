# 场景梳理 001（scenario-framing-001）

## 目标

在 **PRD、`需求文档.md`、功能原型（`需求原型.html`）之前**，产出一份 **单文件 HTML 场景梳理页**，让业务、研发、测试在较短时间内理解：

- 为什么做（背景 / 痛点 / 价值）
- 现在怎么做（现状流程）
- 打算怎么做（方案轮廓）
- 谁负责什么（**角色与职责**，有信息则必写）

**不讲清楚不堆砌**：短句、要点、示意图为主；**禁止**大段散文、**禁止**会议流水账式摘要。

## 何时使用

- 用户触发 **场景梳理001** / **框架梳理001**（见 `description`）
- 用户拖入 `文件夹/需求/…` 或 `文件夹/项目/…` 下文件，要求「梳理场景」「对齐需求」「做方案说明页」
- 用户回复待确认问题后要求 **更新场景梳理** / **按回复定稿**

## 与其它 Skill 的边界

| Skill | 本 Skill |
|-------|----------|
| `requirement-evaluation` / `requirement-doc` | **不**生成或链接 `需求评估.md`、`需求文档.md` |
| `requirement-prototype` | **不**做 ERP 筛选+表格操作原型；仅叙事与示意 |
| `prototype-annotation` | **默认不**注入红点/页面说明 |
| 旧版 `原型/*-方案说明.html` | **不修改** `原型/`；新产出只进 `方案/` |

## 执行流程

### 0. 读取本 Skill 的参考

- 页面结构与图示手法：[reference.md](reference.md)
- 质量标杆（图文密度，**禁止照抄业务内容**）：`文件夹/需求/商超3p需求/原型/WFS共享库存与自动借货-方案说明-v2.html`

### 1. 定位「需求/项目根目录」

1. **优先**从用户拖入对话的文件路径解析：
   - 匹配 `文件夹/需求/{名称}/` 或 `文件夹/项目/{名称}/`
   - `{名称}` 为直接子文件夹（如 `商超3p需求`、`全渠道管报`）
2. 若用户仅粘贴文字，检查是否写明路径；否则用**当前编辑器打开文件**所在路径向上回溯至上述根目录。
3. **仍无法确定**：明确提示用户「请拖入该需求/项目文件夹下的任意文件，或说明路径如 `文件夹/需求/商超3p需求`」。

### 2. 确保 `方案/` 目录存在

- 路径：`{根目录}/方案/`
- 不存在则创建（仅创建目录，不批量生成其它文件）。

### 3. 收集输入（不写会议摘要）

- 读取用户粘贴内容，及根目录下用户指向的文件（如 `原始需求/`、`方案/*.md`、会议纪要 txt 等）。
- **禁止**单独增加「会议要点 / 会议摘要」章节。
- 只提炼为**结构化场景**（背景、痛点、现状流程、价值、方案、角色等）。

### 4. 提炼「主题」与文件名

- **主题**：从用户表述、文件名、文件夹名自动提炼（中文短语，约 4～20 字，可作页面主标题核心词）。
- 清理非法文件名字符：`\ / : * ? " < > |` 等。
- **基础文件名**：`{主题}-场景梳理.html`
- **版本规则**（见 [reference.md § 版本与覆盖](reference.md#版本与覆盖)）：
  - 首次：`{主题}-场景梳理.html`
  - 再次**全量**调用本 Skill 且 `方案/` 下已存在该主题的 `*-场景梳理*.html` → 递增 `-v2`、`-v3`…
  - 用户**回复待确认**后更新 → **覆盖**用户指定或对话中正在迭代的那一份（不自动升版本）。

### 5. 置信度与「待确认」

- **正文**：只写高置信、已对齐的业务事实与方案轮廓。
- **必须**保留独立章节（建议 `id="open"`）：**待确认 / 开放问题**
  - 列出尚未拍板项；
  - 对需求提出方/用户**可直接提问**（编号列表，便于回复）。
- 含待确认时，页顶显示**草案黄条**：`草案 · 含 N 条待确认`（定稿后删除或改为「已定稿 · 更新于 YYYY-MM-DD」）。

### 6. 生成 HTML

**技术**

- 单文件；`<style>` / `<script>` 内联；**不依赖外部 CDN**（兼容 GitHub Pages 与本地 HTTP）。
- **禁止** Mermaid、禁止外链图表库。
- **禁止** `prototype-annotation` 运行时，除非用户明确要求。

**内容与版式**

- 顶部：**一句话**（hero）+ **sticky 锚点导航**（链到各 `section id`）。
- 默认**一个 HTML、多章节**；用户明确要求后再拆分多文件。
- 章节按信息量选配，**非固定全套**；建议优先考虑：
  - 一句话 / 阅读指引（约 X 分钟）
  - 背景 · 痛点 · 现状流程 · 业务价值 · 方案要点
  - **角色与职责**（有角色信息则写）
  - 待确认 / 开放问题
- 每项用 **短句 + 卡片 / 泳道 / 管道图 / 对比表 / Tab / 轻量计算器** 等表达；形式不限，**以讲清楚为准**（参见 reference.md）。
- 文案：自然中文业务语言；对齐 `.cursor/rules/prototype-hint-plain-language.mdc`（用户可见处不写内部字段名、API 名）。

**示例数据**

- 涉及店铺、SKU、区域、渠道等时，**必须**查阅并沿用：
  - `文件夹/规范/销售主数据-全局业务规范.md`
  - `文件夹/规范/基础数据/`（如 `渠道店铺基础数据_v1.json`、`销售主数据索引_v1.json`）
- **禁止**随意编造店名、SKU；常用示例：`H6065301` / model `H6065`、`Govee_US`、`Goveelife_*` 等。
- **去掉**会议纪要中的人名；规范店名可保留。

### 7. 写入文件

- 保存至：`{根目录}/方案/{文件名}.html`

### 8. 更新 GitHub Pages 预览目录（必须）

按 [reference.md § 维护 index.html](reference.md#维护-indexhtml) 更新：

- 根在 `文件夹/需求/` → `文件夹/需求/index.html`
- 根在 `文件夹/项目/` → `文件夹/项目/index.html`

在对应需求/项目行追加链接；无行则新增 `<tr>`。链接使用**相对路径**（相对 `index.html`）。

### 9. 交付说明（回复用户）

简要给出：

- 本地相对路径与文件名
- 是否含待确认及条数
- 推送 `main` 后的 GitHub Pages 入口（`文件夹/需求/index.html` 或 `文件夹/项目/index.html`）
- 若为用户回复后的**覆盖定稿**，说明已收敛待确认项

---

## 待确认 → 定稿（覆盖模式）

当用户在同一会话或新会话中**回答待确认问题**并说「更新场景梳理」「按回复定稿」等：

1. 读取目标 HTML（用户指明路径，或默认 `方案/` 下最新一份该主题的 `*-场景梳理*.html`）。
2. 将高置信结论并入正文；已解决项从「待确认」删除或标为已关闭。
3. **覆盖保存同一文件**；更新页内定稿日期；移除或更新草案黄条。
4. **不必**新增 `-vN` 文件，**不必**重复登记 index（链接路径不变）。

---

## 全量重新梳理（新版本模式）

用户再次触发 **场景梳理001** 且未要求「只更新待确认」时：

1. 扫描 `方案/*-场景梳理*.html` 中与当前**主题**匹配的文件。
2. 若已存在，计算下一版本号，输出 `{主题}-场景梳理-v{N}.html`（无 v1 后缀的首个文件视为 v1）。
3. 在 `index.html` **追加**新链接（保留旧版链接，便于对比）。

- [ ] 含锚点导航与「一句话」hero
