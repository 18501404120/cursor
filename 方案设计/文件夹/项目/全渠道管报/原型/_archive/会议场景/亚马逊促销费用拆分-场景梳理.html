亚马逊促销费用拆分 · 场景梳理

全渠道管报 · 亚马逊渠道 · 2026-06-16 会议对齐 · 约 8 分钟阅读

一句话：管报底层明细表需将亚马逊促销折扣从「总额」拆成 Coupon / Promotion / Deal 三类（首期不细到具体玩法），并汇总到 SKU；Coupon 与 Promotion 取自促销报告，划线价类 Deal（BD / DOTD 等）用 RRP − 成交价 倒算，月内按天更新、定稿后与财报对齐。

示例店铺：Govee_US · 示例 SKU：H6065301（model H6065）

1 · 背景

全渠道管报正在建设底层费用明细表，亚马逊渠道的「促销折扣」需要从财报的统一折扣费中拆出结构。

使用方 销售 / 运营需按 SKU 查看各促销资源投入，支撑月中策略调整与达成跟踪。
与财报关系 财报按成交价计销售额、折扣合并为折扣费；管报按 RRP 计销售额、把中间差额拆成各促销类型。
首期范围 只拆 Coupon / Promotion / Deal 三大类，不细到「买一赠一」「满减 X%」等玩法。
验证样本 2025 年 5 月 Govee_US 促销总额约 70.7 万，与后台可下载报表大数基本一致。
2 · 痛点
类型不可见 财报 / 交易报告把折扣合并，无法区分 Coupon、站内 Promotion、Deal 等资源形态。
报告覆盖不全 BD、DOTD、Deal of the Day 等划线价促销不出现在促销明细报告，需另算。
粒度不够 促销报告只有订单号，无 SKU；一订单多 SKU 时还需分摊。
命名混乱 促销描述由运营自行命名，系统无法仅靠关键词稳定识别类型。
口径时差 按天拉取的结算数据与月定稿财报存在变动，亚马逊历史订单甚至数年后仍会调整。
运费混入 促销报告中含 Shipping Credit 等运费相关抵扣，需与促销费拆开。
3 · 现状流程
销售运营
在亚马逊后台创建促销（Coupon / Promotion / Deal 等）→ 自行命名 → 月中实时看销量与促销达成
数据 / 研发
从 Settlement 取平台费用 → 促销面板爬取活动元数据（BD/DOTD 等）→ 销售报表取折扣金额字段
财务
每月 3～5 号下载亚马逊财务报告定稿 → 以 Settlement 口径确认收入与折扣
现状：财报视角
销售额 = 成交价 × 数量；折扣 = 合并折扣费；不区分促销类型。
目标：管报视角
销售额 = RRP × 数量；Coupon / Promotion / Deal 分别列示；净收入与财报接近可控。
4 · 业务价值
资源可视各促销类型费用汇总到 SKU，看清「钱花在哪类活动上」。
月中可调不必等月底，1～15 号即可跟踪促销投入与达成。
与广告对齐划线价、Coupon、Promotion 均视为促销资源投入，纳入同一分析框架。
定稿可对齐月定稿后用财务报告重算，保证与财报最终一致。
5 · 促销类型与识别规则（首期）
Coupon Promotion Deal（含 LD / BD / DOTD） 运费相关 · 单独剔除
类型 典型场景 是否在促销报告 识别 / 取数方式
Coupon 客户领取的优惠券抵扣 是 促销报告 description 含 coupon 字样
Promotion Save X%、满减、Buy 2 Save 5% 等 是 排除 Coupon、Deal 命名后，其余归入 Promotion
Deal · LD Lightning Deal 待验证 客服称含在 promotion 报告；需确认命名规则后排除
Deal · BD / DOTD Best Deal、Deal of the Day 否（划线价直接扣减） RRP − 促销成交价 × 数量；活动信息从促销面板爬取
Shipping Credit 运费收入代收再抵扣（如 Free Shipping） 混在促销报告 按 description 过滤（Free / Shipping 等），归入运费收入而非促销

平台手续费不在促销费内，仍走平台服务费科目；Coupon / Promotion 是给 C 端用户的折扣，不是平台向卖家另收的费用。

6 · 数据来源对比

Promotion 报告（交易报告 promotion 列展开）

  • 含 Coupon、Promotion 及大部分可命名促销
  • 粒度：订单级，无 SKU
  • 与 Settlement 总额接近（5 月样本差约 2～4 万，含运费项待拆）
  • 存在重复行、部分折扣在订单详情找不到等异常，需清洗

发货报告（Shipment / FBA 发货）

  • 字段 item-price-discount 直接给出 SKU 级折扣金额
  • 通过 shipment-item ID 可关联到 SKU
  • 无促销类型，且不包含划线价类 Deal
  • 5 月总量约 63 万，低于促销报告 70 万——覆盖范围不完全一致

促销面板（后台爬取）

  • 唯一能拿到 BD / DOTD / Deal 等活动清单的方式
  • 报表接口拿不到这些活动的完整列表
  • 与管报已有促销面板逻辑可联动，RRP 由 GTM 统一维护

财务 Settlement 报告（月定稿）

  • 财务每月 3～5 号下载，作为最终对齐口径
  • 运费收入取 Shipping Credit 等字段
  • 管报月定稿后需用此数据整月重算并替换此前按天累计的结果
7 · SKU 维度拆分方案

明细表需汇总到 SKU（可上卷至 SPU / model），两种路径：

路径做法优点局限
A · 促销报告 + 反查 促销报告取订单号 → 关联订单 / 发货报告得 SKU → 按金额分摊 可区分 Coupon / Promotion / Deal 类型 一订单多 SKU 需分摊规则；同订单多行促销难区分具体 SKU
B · 发货报告直取 直接用 item-price-discount，已有 SKU SKU 准确、无需反查 无类型；不含 BD/DOTD；与促销报告总额有 gap

倾向方案：类型拆分走促销报告 + 命名映射；SKU 归属优先通过发货报告 shipment-item ID 关联；BD/DOTD 用 RRP 倒算后按活动 SKU 写入 Deal 列。

8 · 时间口径与定稿机制
月内每天按天更新
拉取前一日 Settlement 数据更新收入段（净收 → 销售额 → 销量）；销售月中看 1～15 号达成。费用段（含促销拆分）可按月汇总，月初有数即可。
月内任意日数据会变动
亚马逊报告非实时：今天拉昨天的数，过两天同一日期金额可能变化；历史订单甚至数年后仍可能调整。日累计与最终月总和允许有小差异。
次月 3～5 号定稿替换
财务下载完整 Settlement 报告 → 管报用财务数据整月重算 → 替换此前按天累计结果，与财报完全对齐。

广告等指标当前取订单报告（非严格发货口径）；管报收入段与财报对齐逻辑一致，以 Settlement 为准。
