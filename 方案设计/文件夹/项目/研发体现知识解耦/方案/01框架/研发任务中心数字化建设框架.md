# 研发任务中心数字化建设框架

## 一、文档信息

| 项目 | 内容 |
| --- | --- |
| 文档名称 | 研发任务中心数字化建设框架 |

| 编制日期 | 2026-09-11 |

本文只承接当次会议精神：公司要把管理对象从「事 / 项目 / 节点」转到「人 / 可验收任务 / 数字化参数」。后续原型与详细方案在本框架确认后再展开。

---

## 二、一句话方向

**以人为中心建设任务中心：按最终量产态把 PRD 解耦成 10～20 个可独立验收的大任务，用字段把需求、约束、验收写清楚；项目只做汇总，人只对任务负责。**

配套判断：

1. 关键角色**必解**，讨论的是怎么解、何时激活，不是能不能解。
2. 真正的研发数字化是 **任务数字化 / 元器件数字化**，不是把 PRD 做成电子文档。
3. 任务中心是第二套协作操作系统；研发中台负责沉淀复用，二者面向人，但职责分开。

## 三、为什么现在必须建

### 3.1 现状判断

| 现状 | 会议口径 |
| --- | --- |
| 立项和逆向已进项目平台 | 过程管理仍大量靠 Excel 和口头沟通 |
| 研发过程不可观测 | 能看见的主要是项目节点，看不见任务级参数、变更和验收 |
| 协作是串行耦合 | 结构 / 电子 / 光学等天然约束强，前人做完后人才开工 |
| 任务颗粒度错位 | 现有「任务」偏节点下的细活（一两天），没有闭环，不能独立验收 |
| 验收能力偏弱 | TE / QE 未按任务前置准备，品质验收没有成为研发加速器 |
| 中台接不住沉淀 | 以项目颗粒度跑完，产不出可复用的模块化结果 |

### 3.2 要解决的本质问题

不是「再做一个更细的项目任务清单」，而是让每一项研发工作变成：

```text
责任人清晰
  + 需求/约束/验收被字段化
  + 可独立验收（面向量产条件）
  + 可观测、可变更扩散
  = 闭环任务
```

只有闭环，才可观测；只有可观测，才谈得上数字化，也才谈得上两年后 AI 进场帮人。

### 3.3 两条必须同时看见的建设主线

会议把「研发数字化」拆成两条线，**不要混成一个系统**：

| 主线 | 管什么 | 适用面 | 本框架定位 |
| --- | --- | --- | --- |
| 信息层：项目信息库 | PRD、图纸、规格书、试验报告、工厂标准、检验规范等可调用资料 | 所有项目 | 任务的**上下文底座** |
| 协作层：任务中心 | 面向人投放、激活、验收、汇合、变更扩散 | 先试点，再全 BU | **本文主体** |
| 能力层：研发中台 | 方案货架、模块标准化、历史方案复用 | 任务闭环结果的沉淀 | **不在任务中心内部实现** |

信息层解决「不再靠文档当面传递、工程师可直接调用」。  
实物层（关键元器件独立验收）解决「能隔离的模块不必等整机才能开发和验收」。  
任务中心把上述能力接到**人**身上：谁领任务、按什么字段做、按什么条件验。

## 四、核心思想

### 4.1 以人为中心，而不是以事为中心

| 旧惯性 | 会议要求 |
| --- | --- |
| 先问这件事能不能拆、能不能解耦 | 关键角色必解，只问如何解、边界和约束是什么 |
| 人在项目里跑节点、开会、等上游 | 人领可验收任务，条件成熟才激活开工 |
| 能力沉淀在项目经验里 | 沉淀在岗位和人身上，再标准化给下一波人 |
| 公司优化「把事做顺」 | 公司优化「给人分配任务和资源」 |

直接研发是领任务的人；间接研发（如 DQE、测试）**不领任务**，跟着任务走。  
每个任务通常 1 个主角色 + 2～3 个辅助角色，保证能调资源，但不把公司平台做成全员细任务系统。

### 4.2 面向验收，而不是面向节点

- 任务必须有封闭性：交得出、验得了。
- 验收默认对准**量产条件**（或明确的市场验收条件），而不是中间 CD / CT 节点。
- 同一独立对象**禁止按阶段拆成两个任务**（例如「先做一版、节点后再做一版」）——那仍是在跑项目。
- 有依赖时，用**推迟激活**处理，不用拆阶段任务。

### 4.3 项目水到渠成，不是人的工作入口

- 对人：任务中心是入口，眼里没有项目列表，只负责任务分配与完成。
- 对项目经理 / 组委会：组委会可同时管理**多个项目**；每个项目各自解耦、可分批发布、可中途增补独立任务。项目视图只做汇总容器。
- 项目颗粒度只用于汇总，不用于驱动日常工作。
- 中长期方向：上下文足够后，「立项会」不再是开工门槛；拿到已描绘清楚的任务就可以开工。

### 4.4 解耦的艺术

解耦不是把项目 WBS 拆细，而是：

1. 产品经理带着高质量 PRD，与项目经理一起，围着**最终量产的那一台机器**反拆任务。
2. 一个项目只允许拆出 **约 10～20 个大任务**（对应约 6～7 个关键角色，有人领 1 个、有人领 2～3 个）。
3. 更细的打样、CMF、对结构接口等，包在大任务内部，由主责人带小团队自己协调。
4. 与某核心任务强相关的附带工作打进该任务；完全独立的小项仍要单独抛出，避免遗漏。
5. 公司平台只开到「人为中心」这一层，不管二阶拆分。

## 五、总体架构

```text
                         ┌────────────────────────────────┐
                         │     公司管理对象：人 / 岗位      │
                         └────────────────────────────────┘
                                          │
              ┌───────────────────────────┼───────────────────────────┐
              ▼                           ▼                           ▼
     ┌─────────────────┐         ┌─────────────────┐         ┌─────────────────┐
     │ 上下文 / 信息库  │         │    任务中心      │         │    研发中台      │
     │ PRD、图纸、规范  │ 提供上下文 │ 投放·激活·验收  │ 闭环沉淀 │ 模块/方案货架    │
     │ 报告、检验标准   │ ────────►│ 变更扩散·看板    │ ───────►│ 标准化后复用     │
     └─────────────────┘         └─────────────────┘         └─────────────────┘
                                          │
                          ┌───────────────┼───────────────┐
                          ▼               ▼               ▼
                     组委会看板        我的任务         项目汇总
                   （投放/激活）     （人的入口）     （只读汇总）
```

### 5.1 三层对象

| 层 | 对象 | 说明 |
| --- | --- | --- |
| 上下文层 | PRD 及项目信息库 | 产生任务、理解参数的语料；**不在任务中心管理** |
| 任务层 | 可验收任务 | 每任务 4～6 个关键项（参数 + 验收条件）；人在这里工作 |
| 汇合层 | 样机 / 市场等系统性验收 | 不为跑节点，为修订参数并做影响扩散 |

### 5.2 与现有项目平台的关系

| 能力 | 现有项目平台 | 任务中心 |
| --- | --- | --- |
| 主视角 | 项目 | 人 / 任务 |
| 已有能力 | 立项、逆向等 | 新建 |
| 过程管理 | Excel / 口头 | 任务字段 + 状态 + 验收 |
| 任务粒度 | 偏细、偏节点、无闭环 | 大颗粒、可验收、可观测 |
| 对人的入口 | 项目列表 | 任务中心 |
| 项目怎么用 | 主工作台 | 汇总容器，不是日常入口 |

一期：**并行**，不指望在现有项目工单里「把任务开细」来代替任务中心。会议判断是：在当前项目颗粒度上做数字化，做不到任务数字化和元器件数字化。

## 六、任务模型

### 6.1 什么才叫一个任务

同时满足以下条件才允许作为公司级任务投放：

1. **有主责人**：直接研发，能领、能交、能被验收。投放时必须写清**任务名称、任务内容、责任人、参数和验收条件**；该条任务发布前可编名称/内容/责任人，**该条发布后**这三项冻结。尺子始终由组委会维护。项目已投放后仍可增补新的独立任务。
2. **有封闭性**：面向一个可验收对象（如 ID、某关键元器件、某独立模块），不是流程步骤。
3. **有数字化描述**：每任务约 4～6 个关键项（交付对象、量产向指标、接口/约束、可执行验收条件）。全项目合计可观测即可，不铺满表单。
4. **面向量产（或明确的市场）验收条件**，而不是「先过某个内部节点」。
5. **粒度够大**：全项目合计约 10～20 个；更细的工作留在任务团队内部。

反例（不允许作为公司级任务）：

- 某元器件的「第一阶段方案」和「第二阶段方案」拆成两个任务
- 「开个会」「提个资料」「等结构出图后再说」这类不可验收事项
- 测试、DQE 日常跟线（它们是任务的跟随能力，不是独立领用任务）
- 把项目经理原来的底层 WBS 原样搬进系统

### 6.2 任务数字化：真正要数字化的东西

```text
PRD（上下文，用来产生和理解任务）
        │
        ▼
任务关键项（每任务约 4～6 个）──── 交付对象 / 量产向指标 / 接口约束
        │
        ├── 验收条件      ──── 组委会确定并输入；性能 / 可靠性等可执行标准
        ├── 验收记录      ──── 提验后由 TE 落记录；不通过回到已开工
        └── 责任结构      ──── 主角色 + 2～3 辅助角色 + 跟随的 TE/QE
```

会议强调：

- **PRD 数字化不是研发数字化。** PRD 是用户需求上下文；电路板、元器件、结构件上的参数才是专业本身。
- 投放时组委会 / 总工按量产态把参数和验收条件写对。主责人只读尺子、推进任务、确认完工；可**向组委会提改参**，确认后由组委会改同一对象字段。**上下文（PRD / 图纸 / 规范）不在任务中心管理。**
- 跨组提需求，只允许提资源、时间、接口和指标，**不得干涉对方任务内部技术实现**。

### 6.3 参数可观测（正向设计能力）

假设一个项目拆 20 个任务、每任务约 4～6 个关键项，全项目约 80～120 个可观测参数：

| 观测 | 含义 |
| --- | --- |
| 解耦时写下的参数 | 理论设计 / 正向定义 |
| 量产落地后的参数 | 真实结果 |
| 匹配数量 / 匹配率 | 解耦正确率，也是研发效率的核心观测 |

汇合和独立验收的目的，都是为了把这批参数改对，而不是为了走完一套节点流程。

字段来源（已拍板）：

1. 组委会按 PRD 投放时写入任务名称、内容、责任人、4～6 个关键参数、验收条件  
2. 主责人发现尺子有问题，**向组委会提改参**；组委会确认后改同一对象  
3. TE 在主责确认完工后落验收记录；不通过先落记录，任务回到已开工，组委会改尺子（或主责按原尺子返工）后再确认完工。验收中途不改条件。TE 不建议改参  

产品侧不必、也填不完所有技术字段——组委会里有各线 Leader 和总工补专业数字，不把尺子交给主责人边做边定。PRD 质量仍须提高，否则投放参数会反复改。PRD / 图纸 / 规范不进任务中心。

## 七、任务生命周期

**每条**任务对象只创建一次，之后沿状态单向往前。验收或汇合发现偏差时，箭头指回「写入」，更新同一对象已挂上的字段，不把该对象拆成下一阶段任务。允许中途**增补新的独立任务**。汇合是系统级横切事件，不是状态机上的下一圈。

```text
写入（组委会写任务 + 参数 + 验收条件；允许中途增补独立任务）
  → 发布该批待发任务（可见，未必开工）
  → 开工（组委会闸门）
  → 主责按尺子推进任务
  → 确认完工 / 提验（主责闸门）
  → 独立验收（TE 落记录）
  → 对象闭环（终点）

改参：验收不通过 → 先落记录 → 回到已开工 → 主责与组委会对齐 → 组委会改尺子 → 主责再干并再次确认完工 → 再验
主责也可在执行中提改参，组委会确认后改；验收中途不改条件
汇合改参：同样由组委会写回已挂字段，不新开任务
横切：样机 / 市场汇合同时切过多条任务，改参并扩散
```

### 7.1 发布 ≠ 开工 ≠ 提验

| 动作 | 谁 | 含义 | 对人的影响 |
| --- | --- | --- | --- |
| 发布 | 组委会 | 任务已存在 | 可阅读任务参数，不强制进项目组开会 |
| 开工 | 组委会 | 约束和输入已够，可以做 | 主责按已定尺子推进任务，不对尺子负责 |
| 确认完工 / 提验 | 主责人 | 认为已可交验 | 尺子冻结；TE 才能交验收记录 |

原则：

- **允许中途增补独立任务**：发现遗漏或新的可验收对象时，组委会可再拆一条。新增必须可独立验收，仍走写入 → 发布 → 开工。已发布任务的名称、内容、责任人冻结。
- 禁止按 CD/CT 节点把同一对象拆成下一阶段任务；依赖不够就推迟开工。
- 对已发布任务，中途做开工、组委会改尺子、确认完工、变更扩散。
- 开不了工就不要开工；过早拉进项目组开会，会破坏独立工作状态。
- 未确认完工，不得验收。开工不等于可验收。
- **尺子归组委会**：主责人界面只读参数和验收条件；要改必须先对齐。

### 7.2 汇合点

会议明确：独立验收之外，还要有系统性验收。汇合**不是 CD 节点管理**，而是阶段性把系统凑在一起，看参数、改参数、做影响扩散。

| 汇合点 | 会议表态 | 备注 |
| --- | --- | --- |
| 样机 | 明确 | 系统性验收 |
| 市场 | 明确 | 更接近真实验收条件 |
| 第三个 | 提到「三大汇合点」 | 候选：试产 / 小批量，**待组委会确认** |

组委会看的是：相关任务是否跑到可汇合的条件。条件满足就汇合，不为「日历上的节点」而汇合。

### 7.3 变更机制

| 类型 | 处理 |
| --- | --- |
| 公司级尺子改参 | 主责可提申请；组委会确认后改参数 / 验收条件。验收中途不改。TE 不建议、不改数字 |
| 影响其他任务的指标 / 接口 / 关键约束 | 必须扩散；涉及计划、资源、其他组目标时开会对齐 |
| 跨组提需求 | 只提资源、时间、接口结果，不干涉对方内部实现 |
| 组内解决不了的资源 / 时间 | 升级到项目组织 / 组委会做倾斜 |

一期变更扩散以「可登记、可通知、可追踪」为主，不做复杂自动影响树。

## 八、组织机制：任务中心组委会

每个 BU 成立任务中心组委会。系统是组委会的工作台，不是替代组委会做解耦判断。

### 8.1 组成（会议口径）

| 进入组委会 | 不进入组委会 |
| --- | --- |
| 各线 Leader | DQE 组员（跟随任务即可） |
| 全部产品经理 | 间接研发全员 |
| 全部项目经理 | — |
| DQE Leader | — |

总工需要进入任务参数的定义与确认——解耦正确率首先是总工 / 理论设计能力的体现。是否单列席位，试点时明确。

### 8.2 组委会职责

1. **解耦**：可同时对多个项目解耦。每个项目按 PRD 和量产态，拆出 10～20 个可验收任务，写清名称、内容、责任人、参数和验收条件。  
2. **投放 / 发布**：把待发布任务交给直接研发，配 2～3 个辅助角色。可多次发布新增任务。禁止按节点给同一对象加单。  
3. **开工**：看看板状态，判断何时开工。一期人工判断。开工不等于可验收。  
4. **确认改参**：主责或验收/汇合发现问题后，组委会改同一对象上的尺子并做必要扩散。  
5. **资源投放与倾斜**：任务 combos 缺资源时协调，而不是让每个人直接找「项目」。  
6. **汇合决策**：条件到了就做系统性验收。  
7. **变更扩散**：跨任务参数变化时组织影响评估。  
8. **保护独立工作状态**：减少无效会议，避免人尚未激活就被项目绑住。

解耦能力本身是组委会的专业，不要求系统一期自动拆任务。

### 8.3 角色分工

| 角色 | 在任务中心中的位置 | 交付 |
| --- | --- | --- |
| 产品经理 | 组委会成员；带 PRD 参与解耦 | 高质量 PRD（上下文） |
| 项目经理 | 组委会成员；总集成、未解耦信息层串接、汇合 | 汇合组织、变更扩散、汇总视图 |
| 直接研发（结构 / 电子 / 光学 / ID 等） | 领任务的主角色 | 按已定尺子推进任务、确认研发完工；可向组委会提改参，不改尺子 |
| 辅助角色 | 配进任务，帮助主责人调资源 | 任务内协同 |
| DQE / 测试等间接研发 | 不领任务，跟随任务 | 验收与质量支持 |
| TE / 实验室 | 跟着任务走 | 提验前看条件、准备设备；确认完工后才交验收记录 |
| 总工 | 参数与解耦正确率 | 量产态字段质量 |
| 数字化 | 建设任务中心一期能力 | 看板、任务对象、发布/激活、验收协同 |

结算原则（方向，细则待人事 / 试点）：直接研发按任务结算；间接角色跟随任务参与，不单独领公司级任务。

---

## 九、验收能力建设

任务中心被明确为 **面向验收的任务中心**。验收弱，研发迭代就会慢。

### 9.1 两级验收

| 级别 | 对象 | 目的 |
| --- | --- | --- |
| 任务级独立验收 | 单个闭环任务 / 关键模块 / 元器件 | 不依赖整机即可验证 |
| 系统级汇合验收 | 样机 / 市场等 | 改参数、看兼容与系统正确性 |

独立验收用标准工装 / 标准方案的，应尽量不绑整机结构或整机 PCB。

### 9.2 验收不通过

必须先落**验收记录**（验项、目标/实测、通过与否、TE、时间）。不通过后任务回到已开工：主责与组委会对齐，由组委会改尺子（或主责按原尺子返工），再次确认完工后才能再验。验收中途不改条件。TE **不建议改参**、不改数字。再验是新记录，不覆盖旧记录。

### 9.3 TE 如何跟着任务走

任务一旦进入可预见开工：

1. TE 在任务中心直接拿到任务，而不是事后从项目里找。  
2. 同步准备实验室、工装；可阅读验收条件，**不能交记录**。  
3. 主责确认完工后，按数字化验收字段检，结果必须回写。

一期系统至少做到：任务对 TE 可见、验收条件可阅读、提验后验收结果可回写。实验室排程与设备能力可以先线下。

## 十、系统能力框架（数字化建设切分）

任务中心一期追求「组委会能投、人能领、验收能跟、过程能看见」，不追求自动编排研发流程。

### 10.1 一期（先做基本面）

| 能力 | 做什么 | 明确不做 |
| --- | --- | --- |
| 个人任务中心 | 直接研发入口：只读参数/验收条件、提改参、确认完工、验收记录 | 不以项目列表做人的首页；主责不改尺子；不在本系统管理上下文 |
| 组委会工作台 | 多项目列表；按项目拆任务并写入参数/验收条件；可中途增补独立任务再发布；开工、确认改参、看板、汇合 | 不自动拆任务、不自动开工 |
| 任务对象 | 主责 / 辅助角色 / 组委会写入的 4～6 关键项 / 验收条件 / 验收记录 | 不管任务内部二阶 WBS；不挂上下文 |
| 发布 / 开工 / 提验 | 三道闸门分开：可见 ≠ 开工 ≠ 可验收 | 按节点追加；同一对象拆两阶段 |
| 项目汇总视图 | 给项目经理看「某项目下所有任务」 | 不恢复成项目过程管理主轴 |
| 验收协同 | TE 提验前可见、可读条件；确认完工后才能交记录；不通过回已开工，组委会改尺子 | 不先做实验室信息管理系统；TE 建议改参；验收中途改条件 |
| 变更登记 | 参数变更、影响对象、是否需汇合讨论 | 不做完整自动影响分析 |
| 上下文 / 信息库 | 不在任务中心建设 | PRD、图纸、规范另行管理 |

一期看板要能回答组委会三句话：

1. 哪些任务已发布未开工？卡在什么开工条件？  
2. 哪些已开工、是否已确认完工、验收是否回写？  
3. 是否具备某个汇合点的系统性验收条件？

### 10.2 二期（基本面跑通后再做）

- 按任务状态自动建议 / 触发激活  
- 变更影响分析（关键指标、接口、资源、计划）  
- 与研发中台打通：闭环任务结果入库为可复用模块 / 方案  
- 正向设计评分：解耦参数 vs 量产参数匹配率  
- 资源中心：主责人要不到资源时的公司级入口  
- 验收条件与实验室能力的更深度数字化  

### 10.3 远期方向（会议展望，不作为一期范围）

- 上下文足够成熟后，弱化甚至取消「立项会」作为开工门槛  
- 更多独立工作者：公司减少把人绑在项目会议里  
- 任务与元器件数字化足够后，AI 才能进场帮人做设计 / 验证  
- 物理 AI 是更远的产业方向；当前两年的任务是把公司打成「AI 进得去」的状态：人从「事」里解放，对象可观测、可闭环

## 十一、与研发中台的分工（避免再做成项目平台）

```text
任务中心：人正在做的闭环工作
    │  做完、验完、参数稳定
    ▼
研发中台：把结果标准化 / 模块化
    │  下一款产品挑选：复用 / 二开 / 新做
    ▼
新的增量再次进入任务中心
```

约束：

- 中台不在任务中心里实现。  
- 没有闭环任务，中台就没有可复用对象可收。  
- 现有项目平台「走完一个项目」产不出模块，正是要改协作操作系统的原因。

---

## 十二、建设原则（MUST）

1. **人是入口**：研发人员打开的是任务中心，不是项目列表。  
2. **任务必可验收**：没有封闭验收条件，就不是公司级任务。  
3. **大颗粒**：每项目约 10～20 个任务；公司不管二阶拆分。  
4. **允许中途增补独立任务**：发现遗漏可新增公司级任务，必须可独立验收；禁止按 CD/CT 把同一对象拆成下一阶段。新增仍走写入→发布→开工。  
5. **开工才做，确认完工才可验；尺子归组委会**：发布可早；开工等条件；参数和验收条件由组委会写入，主责只读、可提改参；TE 交记录必须在提验之后，验收中途不改条件。  
6. **禁止阶段化拆任务**：同一独立对象不得按 CD/CT 切成多个公司级任务。  
7. **数字化在任务上**：参数、验收条件、验收记录；PRD / 图纸不在任务中心管理。  
8. **直接研发领任务，间接研发跟随**。  
9. **汇合为了改参数**，不是为了恢复节点门禁。  
10. **一期组委会看看板决策**，系统不抢解耦和激活的判断权。  

---

## 十三、试点策略

不等系统完美。会议要求：**先成立组委会，找 1～2 个项目实践；数字化先出第一版，再带着真实投放回去打磨。**

建议顺序：

1. 指定 BU 组委会成员（产品、项目、各线 Leader、DQE Leader、总工）。  
2. 选定 1～2 个项目，按量产态试拆 10～20 个任务，写出字段和验收条件。  
3. 并行开发任务中心一期（我的任务 + 组委会看板 + 发布/激活 + 验收回写）。  
4. 用试点项目真投、真激活、真汇合一次，回头改字段模板和看板。  
5. 再讨论二期自动激活与中台沉淀。

试点时允许保留少量线下习惯（会议、资料传递），但必须把任务对象和参数放进系统，否则仍不可观测。

## 十四、本期明确的边界

| 要做 | 不做 |
| --- | --- |
| 任务中心（人 / 任务 / 验收） | 再做一个「项目过程管理系统」或工作流引擎 |
| 任务级字段与验收数字化 | 把 PRD 电子化当成数字化完成 |
| 组委会人工投放与激活 | 一期自动编排、自动拆任务 |
| 项目汇总视图 | 让项目重新成为研发人员主入口 |
| 与信息库、验收、中台的接口关系 | 在任务中心内做完整 PLM / 中台货架 / 实验室管理 |
| 关键角色必解 | 按「这件事能不能解」做例外清单来逃避解耦 |

## 十五、待对齐（不影响框架先立）

以下内容会议有方向、无最终细则，试点时收口：

1. 三大汇合点的第三点具体是什么（试产 / 小批量 / 其他）。  
2. 任务关键项是否按专业给模板（结构 / 电子 / 光学 / ID / 关键元器件）；数量上已拍板为每任务约 4～6 项。  
3. 总工在组委会中的席位与参数确认权。  
4. 辅助角色如何配置、间接角色如何结算。  
5. 与现有项目平台的数据关系：项目号是否仅作汇总标签。  
6. 资源中心启动时机。  
7. 一期系统是否允许「全量发布 + 激活」，或试点时只发布近期可激活任务（会议更倾向可全发、靠激活控制）。  
8. 信息库如何建设（已拍板：不在当前任务中心内管理上下文）。
