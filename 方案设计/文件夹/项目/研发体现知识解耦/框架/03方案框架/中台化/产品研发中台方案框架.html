产品研发中台：先立货架，再做项目

2

两件事必须拆开

LINE A · 本页主线

中台 / 解决方案

回答：公司已经有哪些能力？新产品用哪套？做完怎么沉回来？

  • 对象是模块方案 + 产品方案
  • 决策发生在组项目之前
  • 这是解耦要达成的组织目的
不是
LINE B · 并行另一条

结构化 / 知识库

回答：字段怎么拆、检索怎么准、AI 怎么认、角色怎么找上下文？

  • 对象是文档切片 / 元字段 / 工作台
  • 服务识别、检索和下钻，不替代货架
  • 已经明确要做，但是另一件事
并行关系：不做中台，结构化也能做；做了中台，结构化会让匹配、检索、AI 识别更准。方案对外先讲中台，避免把工作台 demo 讲成解耦目的。
3

中台要回答的四个问题

Q1 · 货架

已经有什么

各专业沉淀了哪些模块方案，性能指标、通用能力、适用产品分别是什么。

Q2 · 匹配

新产品怎么选

产品需求拆开后，每个模块是直接复用、二次开发，还是立新方案。

Q3 · 分流

项目里做什么

只有新方案和二次开发进入项目拆任务；已复用部分不再从零开发。

Q4 · 回写

做完怎么回来

上市后整机方案回写为产品方案；新能力回写到模块货架，供下一款引用。

5

主流程：项目前决策，项目后沉淀

1

产品定义

产品经理给出性能、上市日期、场景和要求。还不是项目任务书。

2

按模块拆解

对照中台货架，把需求拆到结构、电子、光学等模块清单。

3

匹配拍板

架构师 / 技术负责人逐模块决定：复用、二次开发或新做。

4

增量进项目

只有二次开发和新做拆成项目工作包；复用项只引用方案。

5

上市回写

整机方案写成产品方案；新能力沉入模块货架。

决策怎么分

模块需求对照货架后
复用

直接引用模块方案，不进项目开发清单。

二次开发

基于已有方案改一版，只把增量推进项目。

新做

货架都不满足，先立新方案，再进项目开发。

谁来拍板

现网是结构、电子、光学分头负责，缺组合决策人。中台不能假装系统能替代这个角色。

角色在中台里做什么
产品经理定义产品要求和上市约束，不代替模块选方案。
架构师 / 技术负责人拆模块、对照货架、拍板复用 / 改 / 新做。
各专业负责人维护本专业模块方案，对专业指标负责。
项目侧只执行增量任务，不重新发明已复用方案。
时点要求：匹配和拍板发生在组项目之前。不能等项目拉起后，再让没经验的人在项目里从头设计；否则能力永远沉不回中台。

方案要求清单

编号 要求 验收口径 本阶段粒度
M1 先立「产品研发中台」概念，而不是先做项目工作台。 对外能讲清：中台管复用，项目管增量。 方向必须讲清
M2 模块方案可增删改查，字段覆盖指标、能力、适用产品、文档。 能列出货架，能判断「有没有现成方案」。 先做增删改感
M3 产品方案可增删改查，并绑定产品 / SKU 与模块组合。 能从一款产品回看到用了哪些模块方案。 先做增删改感
M4 产品需求生成后，能拆到模块并关联已有方案。 每条拆解都能落到复用 / 二次开发 / 新做。 讲清关系即可
M5 决策权在架构师 / 技术负责人，不在项目执行岗。 方案写清谁匹配、谁拍板、谁执行。 组织前提需同步
M6 项目只承接增量任务，不把整套方案重新做一遍。 复用项不再进项目开发清单。 讲清分流规则
M7 上市后必须回写，形成「做一款、沉一套能力」。 新产品能引用上一款沉淀的模块 / 产品方案。 闭环必须写进方案
M8 方案卡片先看归纳，再下钻结构化字段和原始文档。 几十个字能判断，质疑时能点开证据。 与知识库衔接，后做细
8

和知识解耦方案框架怎么并存

已有框架

项目内解耦

拆块并行、汇入点、机制规则、字段化、试点沉淀。解决的是一个项目里怎么少等待、少问人、到点汇合。

+
本页框架

跨项目中台

模块货架、产品方案、项目前匹配、上市回写。解决的是公司一层怎么复用能力，而不是每款从零做。

中台选出模块方案→ 增量进入项目解耦单元→ 项目内按条件并行与 JP 汇入→ 上市回写产品 / 模块方案→ 下钻结构化字段与原文

两套框架不互相替代。中台决定「用什么能力」；知识解耦决定「选定之后项目里怎么跑」。方案卡片通过结构化知识库下钻证据。

9

做到什么粒度，以及先不要做什么

本阶段要做

浅层对象关系，能对外讲通

  • 把两层对象、五步主流程、三类决策讲清楚
  • 模块方案 / 产品方案先做到可感知的增删改
  • 用 1 个品类（如照明）试命名和粒度
  • 立项前先跟老板 / 老范对「解耦目的」
本阶段不做细

不要做成完整 PLM

  • 不按完整系统细拆页面、审批流、权限模型
  • 不把角色工作台、协作图、文档切片写成中台主叙事
  • 不假设先有数字化才能做复用；没有系统也可以先立货架
  • 不在目的未对齐前投入细需求

还没拍板、会影响方案对错的点

假设 为什么危险 建议怎么验
老大解耦 = 平台化复用 会议明确这是猜测；猜偏则整套方案错。 立项前先跟老板 / 老范对目的。
必须先有架构师 / 架构部 现网缺组合决策人，系统替代不了拍板。 方案里写组织前提，不假装系统能决策。
模块切多细 切到部门还是切到灯珠级，范围差一个数量级。 先用 1 个品类试命名和粒度。
软硬件是否同一套中台 会议倾向整机都要拆，但视角还不完整。 对象模型先统一，专业字段分域。
