# 研发知识解耦产品架构

> 版本：v0.2  
> 日期：2026-08-17  
> 阅读建议：本文件用于快速看清产品边界和建设阶段；完整功能说明与关键页面示意见同目录 `研发知识解耦产品架构.html`。

---

## 1. 产品定位

本产品不是另一套 PLM，也不是项目经理排任务、催进度的项目管理系统。

> **它是一套研发自主协作平台：让研发项目可以拆成可独立验收的解耦单元，由主责人自主推进；系统负责提供连续上下文、依赖条件、组织能力和汇入验收机制。**

金蝶等 PLM 继续负责需求、文档、物料、BOM、CAD 和工程变更等专业数据。本产品重点解决：

- 谁对一个业务结果负责；
- 主责人有哪些自主权；
- 什么时候具备开工条件；
- 需要哪些组织能力；
- 多个解耦单元何时汇合；
- 上游变化会影响谁；
- 当时使用的版本和验收证据能否复现。

## 2. 简化后的产品架构

产品只保留四层，不再把“集成与记录系统”单独作为一层。

```text
┌────────────────────────────────────────────────────┐
│ 1. 角色工作台                                      │
│ 我的工作台｜主责人工作台｜PM/PD机制台｜JP驾驶舱    │
├────────────────────────────────────────────────────┤
│ 2. 核心业务功能                                    │
│ 项目解耦｜条件工作网｜数字上下文｜JP汇入｜协同调整 │
│ 组织能力｜影响分析｜模板复用｜AI辅助               │
├────────────────────────────────────────────────────┤
│ 3. 统一数据内核                                    │
│ 解耦单元｜知识原子｜关系｜版本冻结｜钉扎｜快照     │
├────────────────────────────────────────────────────┤
│ 4. 平台支撑                                        │
│ 权限授权｜规则｜消息｜审计｜搜索｜外部系统连接     │
└────────────────────────────────────────────────────┘
```

### 2.1 角色工作台

不同角色不需要进入大量后台模块，而是直接看到当前需要处理的事项。

| 工作台 | 主要回答的问题 |
| --- | --- |
| 我的工作台 | 哪些工作可开始、哪些在等待、哪些变化需要评估 |
| 主责人工作台 | 我的目标、授权、输入、输出、能力和下一汇入点是什么 |
| PM/PD 机制台 | 哪些依赖、能力、协同或 JP 存在机制性风险 |
| JP 驾驶舱 | 汇入条件是否齐全、能否通过、谁回退、谁继续 |
| 能力方工作台（二期） | 有哪些能力请求需要响应、何时可以交付 |

### 2.2 核心业务功能

这是用户实际使用的产品能力，分三期逐步建设。

### 2.3 统一数据内核

所有功能共用同一组对象和关系：

```text
项目
 ├── 解耦单元 ── 主责人 / 授权 / 验收
 ├── 工作 ── 输入 / 输出 / 状态
 ├── 知识原子 ── 版本 / 定稿 / 冻结 / 附件
 ├── JP ── 汇入条件 / 结论 / 快照
 ├── 协同与调整 ── 影响对象 / 决策 / 处置
 └── 组织能力 ── 请求 / 承诺 / 交付
```

### 2.4 平台支撑

平台支撑只提供通用能力，不应成为产品主叙事：

- 项目、角色和对象权限；
- 状态与规则计算；
- 消息、待办和超时提醒；
- 操作审计与度量；
- 全局搜索；
- 通过链接、导入或接口连接 PLM、ERP、测试平台等现有系统。

## 3. 三期建设路线

## 3.1 一期：跑通自主协作闭环

**目标**：先证明新协作方式能在一个真实 PD 项目中运行，不追求大而全。

### 一期建设功能

| 功能 | 解决的问题 | 一期做到什么 |
| --- | --- | --- |
| 项目与解耦设计 | 项目仍按岗位和文档串行，责任边界不清 | 划分解耦单元，明确主责人、授权、输入、输出和验证方式 |
| 数字上下文 | 信息散落在文档、群聊和个人电脑 | 建立 A/B 档知识原子、版本、定稿、冻结、附件和组装页 |
| 条件工作网 | PM 靠排期和催办判断谁该开始 | 根据必要输入是否冻结自动判断未就绪、可开始、进行中、已完成 |
| JP 汇入 | 评审材料靠人临时凑，过不过依赖会议经验 | 固化汇入清单、验收规则、回退/继续策略和 JP 快照 |
| 基础协同与调整 | 跨组诉求和重要变化主要靠私聊或临时拉会 | 提供协同单、P0/P1/P2 分级、响应与决策留痕 |

### 一期关键页面

1. 项目解耦地图；
2. 主责人工作台；
3. 项目条件工作网；
4. 知识原子详情；
5. JP 汇入驾驶舱；
6. 协同与调整中心。

### 一期试点范围

- H8120 作为历史样板；
- 1 个在飞 PD 项目；
- KO→CR 全链模板；
- 25～35 个结果型工作；
- A 档约 35 个、B 档约 25 个知识原子；
- 重点跑通 JP-KO、JP-ES、JP-TL、JP-DR；
- 权限先采用“项目成员可看、责任人可改”两档。

### 一期明确不做

- 不做完整 PLM；
- 不做每日任务和工时管理；
- 不自动推导全部依赖；
- 不做复杂知识图谱；
- 不做复杂 ACL；
- 不做 AI 自动验收或自动决策；
- 不做 CAD 插件和全量 ERP/MES 集成。

### 一期成功标准

- KO 后至少两个解耦单元可以不等整机自主推进；
- 输入条件满足后，主责人无需 PM 催办即可识别并开始工作；
- 任一重点 JP 能在 5 分钟内判断是否具备汇入条件；
- 跨组诉求通过协同单形成响应和结论；
- JP 历史可以通过快照复现；
- PM 手工汇总和催问次数明显下降。

---

## 3.2 二期：补齐组织能力和影响闭环

**目标**：在一期机制跑通后，解决“需要谁支持、变化影响谁、经验如何复用”。

### 二期建设功能

| 功能 | 解决的问题 | 二期做到什么 |
| --- | --- | --- |
| 组织能力货架 | 测试、专家、设备、供应商等能力仍靠临时找人 | 能力目录、输入条件、输出承诺、请求、响应、交付和能力缺口 |
| 综合影响分析 | 上游变更后，影响范围主要靠个人经验判断 | 反查受影响的知识原子、工作、解耦单元、JP、能力请求和 GTM 锁定 |
| 模板与复用中心 | 每个项目重新拆解、重新定义字段和 JP | 沉淀解耦模板、工作模板、JP 模板、原子模板和能力模板 |
| 外部对象连接 | 产品数据和协作信息分散在多个系统 | 以代理对象连接 PLM 文档、物料、BOM、测试结果和变更状态 |
| 机制运营度量 | 试点收益只能靠主观感受 | 统计等待时长、协同响应、JP 一次通过、能力复用和 PM 手工协调量 |

### 二期关键页面

1. 组织能力货架；
2. 能力请求详情；
3. 变更影响分析；
4. 模板与复用中心；
5. 机制运营看板。

### 二期成功标准

- 主责人可以从工作中直接申请所需组织能力；
- 重大变化能够在一个页面看到主要影响范围和处置责任人；
- 新项目可以复用已验证的解耦、JP 和知识模板；
- 关键 PLM/测试对象可以被引用并参与工作条件和 JP 验收；
- 可以用数据比较 1.0 与 2.0 的协作差异。

---

## 3.3 三期：形成跨项目智能协作平台

**目标**：基于前两期积累的高质量对象、关系、版本和事件，做跨项目运营与可溯源 AI。

### 三期建设功能

| 功能 | 解决的问题 | 三期做到什么 |
| --- | --- | --- |
| AI 上下文助手 | 新成员和跨组角色理解项目成本高 | 按角色生成摘要、回答问题并返回来源对象和版本 |
| AI 缺口与风险识别 | 依赖缺口和潜在风险仍需要人工逐项发现 | 识别输入缺失、长期等待、能力瓶颈、证据不足和潜在影响 |
| 智能复用推荐 | 历史技术、模板和能力难以主动复用 | 推荐相似解耦单元、知识原子、技术/CBB、能力服务和历史处置 |
| 跨项目能力运营 | 多项目争抢测试、专家和供应商资源 | 查看能力容量、预约冲突、重复缺口和建设优先级 |
| 规则与业务配置 | 不同业务线需要不同模板和规则 | 支持业务类型、字段、状态、JP 和规则的受控配置 |

### 三期关键页面

1. AI 项目上下文助手；
2. 跨项目风险与依赖中心；
3. 组织能力运营中心；
4. 业务规则配置中心。

### AI 使用边界

AI 可以生成摘要、发现缺口和提供建议，但不能直接：

- 冻结知识原子；
- 改写下游钉扎版本；
- 判定 JP 自动通过；
- 代替主责人专业验收；
- 自动批准正式变更。

## 4. 功能之间如何串起来

```text
项目启动
  → 划分解耦单元并授权主责人
  → 建立知识原子和工作输入输出
  → 输入达到冻结要求，工作自动变为可开始
  → 主责人开工并钉住输入版本
  → 遇到跨组诉求发起协同，遇到能力需求申请组织能力
  → 输出定稿并附验证证据
  → 到 JP 检查 A 档齐套、验收、回退与继续
  → 固化 JP 快照
  → 变化时计算影响并形成处置
  → 项目结束后沉淀模板、能力和经验
```

贯穿产品的三条链：

1. **责任链**：项目 → 解耦单元 → 主责人 → 授权 → 结果验收；
2. **条件链**：输入冻结 → 工作可开始 → 输出定稿 → 下游点亮；
3. **证据链**：需求/目标 → 方案/实现 → 测试/评审 → JP 结论 → 变更历史。

## 5. 从金蝶借鉴什么

### 直接借鉴

- 业务对象、元数据和对象关系；
- 生命周期、版本和权限；
- 任务输入、输出和结束条件；
- 检查项和验收证据；
- 基线、差异比较和影响分析；
- 技术货架和成熟度；
- 外部专业系统连接。

### 改造后借鉴

- 项目模板改为轻量解耦模板；
- WBS 任务改为可独立验收的结果包；
- DCP/TR 改为按风险和集成需要设置的灵活 JP；
- 技术货架扩为完整组织能力货架；
- 工程变更扩展到范围、依赖、JP、授权和资源变化。

### 不照搬

- 项目经理统一拆大量 WBS；
- 以甘特图、工时和资源负荷作为主要控制方式；
- 所有团队采用同一流程和任务颗粒度；
- 通过层层审批替代清晰授权；
- 把流程走完视为结果有效；
- 试点期一次性建设完整 PLM；
- 把 AI 生成内容直接当作正式事实。

## 6. 核心对象

| 对象 | 作用 |
| --- | --- |
| 项目 | 承载试点范围、阶段、成员和模板 |
| 解耦单元 | 可独立策划、推进、验证和汇入的业务结果边界 |
| 授权清单 | 明确主责人可以确认、决策、调用和验收的范围 |
| 工作 | 解耦单元在某阶段可独立验收的结果包 |
| 知识原子 | 可版本化、可冻结、可引用的项目上下文 |
| 输入/输出绑定 | 定义工作依赖什么、产出什么、最低要求是什么 |
| JP | 多个解耦单元的汇入验收对象 |
| JP 快照 | 某次汇入时不可修改的版本和证据集合 |
| 协同请求 | 组间正式诉求及响应记录 |
| 调整单 | 范围、接口、依赖、资源、授权等变化的处置记录 |
| 能力服务 | 可被项目申请和复用的组织能力 |
| 外部对象代理 | 对 PLM、ERP、测试等系统对象的轻量引用 |

## 7. 最终判断

产品架构应保持简单：

> **前台围绕角色工作，中间围绕九项业务能力，底层只保留统一对象和通用支撑。**

建设顺序也必须简单：

> **一期跑通自主协作，二期补齐能力与影响，三期再做跨项目运营和 AI。**

任何新增功能都应先回答：它是否直接帮助主责人自主、依赖条件可见、组织能力可获得、JP 可验收或历史可复现。如果不能，应后置或不做。
