# 阶段7：代码增量同步（拉取最新代码后维护知识库）

## 定位
本模式独立于阶段0→6线性流程，属于知识库的**日常维护模式**。
用途：每次拉取前后端最新代码后，基于 git 变更自动识别本系统受影响的内容，逐项确认后维护到已有知识库。
【重要】本模式全程只写入/更新已有文件，禁止新建一级目录；仅在识别到全新页面时，允许在对应模块目录下新建页面详情文档。

## 前置读取
1. 读取当前系统 `./ERP_product/{{系统名}}/知识库/system-config.md`，获取：
   - web_root / web_biz_path（前端业务根，用于过滤本系统变更）
   - backend_root / backend_biz_path（后端业务根）
   - kb_root（知识库根）
2. 读取当前系统 `./ERP_product/{{系统名}}/知识库/run-progress.md` 的【同步状态】区，获取上次同步基线：
   - web_synced_commit（前端上次同步到的 commit）
   - backend_synced_commit（后端上次同步到的 commit）

## 执行步骤

### 第1步：确定同步基线
- 若 run-progress.md 已有 web_synced_commit / backend_synced_commit → 作为本次 diff 起点。
- 若为空（首次启用同步）→ 不做回溯更新，直接把两个仓库当前 HEAD 写入基线，提示用户「基线已初始化，本次无需更新，后续拉取代码后再执行同步」，结束。

### 第2步：计算变更文件清单
分别对前后端仓库执行（只读，不改动代码），命令已限定本系统业务路径：
- 前端：`git -C {{web_root}} diff --name-status {{web_synced_commit}}..HEAD -- {{web_biz_path}}`
- 后端：`git -C {{backend_root}} diff --name-status {{backend_synced_commit}}..HEAD -- {{backend_biz_path}}`
记录每个文件的变更类型：A=新增、M=修改、D=删除、R=重命名。
同时记录两个仓库当前 HEAD（本次同步完成后要写回基线）。

### 第3步：复核本系统范围
- 第2步命令已限定 `web_biz_path` / `backend_biz_path`，本步复核清单中是否仍有误入路径；若有则剔除。
- 若过滤后无任何变更 → 提示「本系统自上次同步以来无代码变更」，仅更新基线，结束。

### 第4步：映射到知识库文档，生成【变更影响清单】
对每个待处理变更文件，除 `--name-status` 外，执行 `git diff {{基线}}..HEAD -- <文件>` 读取**实际改动内容**，再结合路由/模块概要/已有页面详情文档做精映射。映射参考：
- 路由/菜单文件变更 → 可能影响 `01-全局架构/业务模块划分清单.md`、模块概要
- 页面/组件文件（页面目录下）→ 影响 `03-页面详情/{{模块}}/{{页面}}.md`；新增页面→建议新建页面详情文档
- Controller/Service 业务逻辑变更 → 影响对应页面详情的「背后业务规则」、`06-业务规则`
- Model/实体/字典变更 → 影响 `05-数据实体`
- 大范围结构调整 → 影响 `01-全局架构/系统全局认知说明.md`

输出清单表格：
| 序号 | 变更文件 | 变更类型 | 影响的知识库文档 | 建议动作 |
|-----|---------|---------|----------------|---------|
（建议动作取值：更新页面详情 / 新建页面详情 / 更新模块概要 / 更新数据实体 / 更新业务规则 / 更新全局架构 / 无需更新）

对无法确定映射的变更，标注[待人工判断]，不臆造。

### 第5步：逐项确认（沿用主控指令集：继续/跳过/终止）
按清单向用户反问，让用户决定处理哪些项：
「代码增量分析完成，本系统共识别 N 处受影响文档（见上方清单）。是否开始逐项更新？回复【继续】处理第一项，回复【跳过】跳过该项，回复【终止】结束并保存基线。」

### 第6步：逐项更新知识库
对每个确认更新的项：
1. 重新读取变更后的代码文件（对应前端页面/组件或后端Controller/Service/Model）
2. 按其文档类型套用对应阶段模板的结构：
   - 页面详情 → 遵循 step4-page-detail.md 结构
   - 模块概要 → 遵循 step3-module-summary.md 结构
   - 数据实体 → 遵循 step5-db-model.md 结构
   - 业务规则 → 遵循 step6-business-rule.md 结构
3. **只更新受本次变更影响的小节/字段/规则**，未变动内容保持原样，不整篇重写、不扩大分析。
4. 全程业务语言，不出现代码、接口、字段名等技术标识；不确定标注[待确认]。
5. 每更新完一项固定反问是否处理下一项（继续/跳过/终止）。

### 第7步：收尾——写回基线 + 追加变更日志
1. 更新 run-progress.md 的【同步状态】区：
   - web_synced_commit / backend_synced_commit 写为本次两个仓库的当前 HEAD
   - last_sync_time 写当前日期
2. 向 `{{kb_root}}/sync-changelog.md` 追加一条同步记录（文件不存在则创建该文件，非目录，不违反目录约束）：
   ```
   ## {{YYYY-MM-DD}} 同步记录
   - 基线：前端 {{旧web_hash}}→{{新web_hash}}，后端 {{旧backend_hash}}→{{新backend_hash}}
   - 处理：更新 X 处 / 新建 Y 处 / 跳过 Z 处
   - 明细：
     - {{页面/模块/实体名}}：{{本次改了什么}}
   ```
3. 输出收尾语：「本系统知识库已同步至最新代码（前端 {{新hash}}、后端 {{新hash}}），共更新 X 处、新建 Y 处、跳过 Z 处，变更日志已归档。」

## 硬性约束
1. 只处理当前绑定系统范围内的变更，跨系统改动一律忽略。
2. 只增量更新受影响内容，禁止整篇重写、禁止顺手梳理未变动页面。
3. git 操作全部只读（diff / rev-parse），本模式不执行 pull、不改动任何代码仓库。
4. 每项更新后必须反问，禁止自动连续跑完所有变更项。
5. 变更映射不确定时标注[待人工判断]，宁可让用户确认也不臆造。
