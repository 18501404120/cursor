# 如何梳理 EOM 2.0 退市管理流程

这次梳理的对象是 GTM 里的退市管理。材料用的是 2026-09-22 的 EOM 流程 2.0 方案，以及 2026-09-23 的退市管理会议结论。下面按「对象与边界、角色与动作、状态与规则、信息与协同、取舍与确认」把这一次怎么定下来的写完整。

## 1. 先定这次梳理的对象

1.0 把核料放进了 ERP，大约每半年集中发起一次，流程停在计划确认。系统能做的是发起、选品、上传一份方案附件、计划确认。确认之后页面显示完结，并禁止继续下单。清库和反退市仍在线下，库存、库龄、渠道进度、新品和备料散在不同系统，靠人工拼接。清库拖久了，会挡住新品上市。

2.0 要改成按月常态运营，由需求计划把产供销收到一条链上。梳理的终点定在「库存清完并闭环」，起点定在「GTM 线下评估之后发起」。8 位 SKU 作为一张工单里的管理粒度，渠道链接用来核对 Last Buy 和库存明细。

量级也先写上，避免按「每个产品都单独立项」来设计：半年大约 50 个 SKU，从发起到清完最快约半年，多数约八个月。需求计划业务执行只有两人，撑不住每个 SKU 再组一套班子。

## 2. 还原现状时，先找系统停住的位置

现网主路径是：

发起，选择产品 → 上传方案附件 → 核料测算 → 计划确认 → 页面显示完结。

计划确认之后，Last Buy、成品清库、专用料清理、反退市都不在系统里。所以「完结」只表示计划点过确认，不表示产品已经退完。

这一步把断点标在计划确认。后面的梳理只继续追会影响闭环的部分，不把复盘、升级、超权限审批一起画进主流程。

## 3. 把「完成」拆成四种状态

业务口中的完成，对不上同一种状态。方案里拆成四套，彼此不互相代替：

| 要回答的问题 | 用哪套状态 | 退市里怎么走 |
| --- | --- | --- |
| 这张单走到哪 | 工单阶段 | 草稿 → 核料中 → 待方案决策 → 执行中 → 库存清完闭环；正式退市前也可以关闭 |
| 这个产品处于什么状态 | 产品状态 | 提交后进入准备退市；方案生效后进入正式退市；当前库存为 0 进入 EOL |
| 某人的任务做完没有 | 节点任务 | 只有计划确认核料、发起人确认方案会卡住往下走 |
| Last Buy 到没到 | Last Buy 状态 | 无需、未进在途、在途中、已完成。它不单独推动工单阶段，也不决定能不能闭环 |

闭环只看一件事：本单全部 SKU 的当前库存为 0。当前库存含采购在途。专用料还没清理完、Last Buy 还没做完，都不把闭环往后再拖。发起页上另有一个不含采购在途的库存数，两套数不能拿来对账。

## 4. 核对关键动作卡在哪个节点

会上有一句「发起后禁止继续下单」。直接写成规则，方向会反。核对后分成两段：

准备退市阶段，采购仍要下 Last Buy。正式退市之后，不能再下任何采购单。因此 Last Buy 必须在方案确认、状态变成正式退市之前，已经进入在途。

在途检查挂在「确认整单」上。只检查方案里 Last Buy 数量大于 0 的每一个渠道链接，不能用「这个 SKU 已经有任意一张采购单」代替。这一步只看有没有进入在途，不拿方案数量和实单数量比对。检查不通过，工单停在待方案决策，不能生效。

另外两条一起定死：

核料由系统算出呆滞，计划按自己负责的 SKU 确认。全部 SKU 确认后，才进入方案决策。PMC 核对专用料，不卡住这一定版。

备料数据要在方案决策前到位。方案定了再补备料，容易把已经确认的清库方式、下单量和报废量推翻。

超过权限的报废不在系统里审批。系统只做强提示，线下走计委会，不挡住正式退市。反退市只在正式退市之后、由本单发起人发起，审批通过后自动回写并关单。本期不在这条流程里跟踪追加 Last Buy。

## 5. 角色只保留会卡住闭环的动作

| 角色 | 在这条流程里做什么 | 会不会卡住往下走 |
| --- | --- | --- |
| GTM 发起人 | 线下评估后发起，编写并确认清库方案 | 确认整单会卡住正式退市 |
| 计划 | 按 SKU 确认核料；方案里的数量或结论被改过时，再确认一次 | 会卡住 |
| PMC | 核对专用料和物料测算；正式退市后看专用料清理 | 不卡住定版，也不在系统里点清尾完成 |
| 销售 | 在销售系统按退市节奏填后续销量；正式退市后按方案清库 | 不进退市待办。后续销量不能超过全链路库存 |
| 采购 | 准备退市阶段下 Last Buy；正式退市后不能再下单 | 不在退市系统里点完成 |
| 需求计划 | 看工单和台账，组织这条链 | 没有必办待办 |

销售刷新预测只发提醒，不卡住核料。销售、采购、PMC 的清尾进度看台账，系统按库存和在途回写，不要求他们在 GTM 里点「完成」。

## 6. 决策前要到齐的信息，和必须结构化的结论

集成进工单的数据：库存、库龄、渠道进度、新品、Last Buy、供应链备料。这些数用于判断，不单独变成一个审批节点。

从附件里拆出来、必须填成字段的结论：清库方式、Last Buy、下单量、报废量。清库方式包括正常销售、降价、渠道调拨、改制、转卖、报废。方案仍保留附件，但数量和方式不能只锁在文件里，否则版本一变，采购和计划用的不是同一份数。

## 7. 9 月 23 日把范围再收了一次

方案写到 9 月 22 日时，主链已经从计划确认收到了库存清完，销售和采购的清尾也没有做成待办。会上又收了两刀。

第一刀，按有没有明确时间目标拆事项，不再把所有退市都做成同一种立项：

有明确时间目标的，主要是新老品切换。嵌在 GTM 上市项目里，按新品上市时间倒推，不另拆项目，仍是同一班人。

销量、毛利驱动的常态退市，走这条流程。没有严格统一的截止日，按渠道承受能力和物料情况决定消耗、转卖或报废。

后半段仍是同一条链：线下评估后发起 → 核料（系统算呆滞，计划确认）→ 方案决策 → 执行清库 → 库存清完闭环。主动、被动还作为发起类型留下，用来区分要不要维护新品衔接，不再据此生成两套节点。

第二刀，不用流程去推人。原方案里「核料超过 7 天再提醒」不按流程待办落地，时间目标放在 GTM 项目里排。流程上留下的是两个确认：计划确认核料，发起人确认方案。

## 8. 这次梳理留下的取舍

必须进系统：工单从发起到库存清完；计划按 SKU 确认核料；方案在确认前写清清库方式和数量；Last Buy 在正式退市前进入在途；正式退市后禁止再下采购单；库存清零自动闭环；反退市审批通过后回写。

值得进系统：库存、库龄、在途、备料和新品进度集成到决策前；清库方式、下单量、报废量结构化；台账按日看清库进度。

不进系统：用超期待办催人；销售、采购、PMC 在 GTM 点清尾完成；复盘和自动升级；超过权限的报废审批；本期跟踪追加 Last Buy。

待验证：拉会时要找到这个 SKU 的销售负责人，还是只找到主管。会上已经提出，还没有核对完，不先写进规则。
