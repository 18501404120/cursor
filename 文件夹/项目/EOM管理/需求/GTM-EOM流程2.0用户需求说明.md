## 二、需求背景

EOM 已由阶段性的停产确认工作，转变为常态化的产品退市运营工作。业务不仅需要确认产品是否进入 EOM，还需要持续管理新品替代、销售预测、核料、Last Buy、成品库存清理、专用物料清理、异常处置、S&OP 复盘及最终 EOL 闭环。

目前 GTM 系统已经支持发起 EOM、选择产品、上传方案、计划确认、核料及部分测算，但系统流程在计划确认后即结束，后续清库及闭环仍主要依赖 Excel、钉钉沟通和人工催办。现有系统无法完整反映一个 EOM 产品为什么退市、当前由谁处理、执行到哪一步、还剩多少库存和物料、存在什么风险以及何时能够完成 EOL。

因此，需要将当前 EOM 功能从“核料测算加附件审批”升级为覆盖退市全过程的在线管理平台。

## 三、当前存在的问题

### 3.1 流程结束时间与真实业务不一致

当前系统在计划人员确认后即将流程标记为“完结”，但业务上此时只是确认退市及清库方案，产品才刚进入正式 EOM 执行阶段。后续 Last Buy、库存清理、物料清理和 EOL 闭环均未纳入系统。

由此带来的问题：

1. 系统状态不能代表真实业务进度。
2. 管理人员看到“完结”后，无法判断产品是否真正完成清尾。
3. 清库超期、物料未清、Last Buy 未完成等风险被隐藏。
4. EOM 与 EOL 之间缺少可持续跟踪的业务链路。
5. 产品 GTM 发起后无法持续查看清库执行情况，月度复盘时仍需临时向各责任人收集信息。
6. 需求计划无法确认 Last Buy、成品库存和专用料是否真正处理完成。

### 3.2 主动退市与被动退市未区分

当前系统未结构化区分主动退市和被动退市，也未记录退市触发原因、新品迭代关系、新品预计 CR 时间及上市时间。

由此带来的问题：

1. 无法根据不同退市类型生成对应业务流程。
2. 主动退市缺少新老品切换计划，容易出现老品断货或新品上市后老品积压。
3. 被动退市原因依赖附件或备注，无法统计和复盘。
4. LBU、ABU 的发起节奏及责任分工无法在系统中体现。
5. 产品 GTM 发起 EOM 时需要跨系统收集产品、新品和预测信息。
6. 无法快速确认整 Model 下是否遗漏有效 SKU。

### 3.3 EOM 台账依赖线下维护

业务需要的产品、预测、库存、Last Buy、物料及清库信息分散在多个系统和线下表格中，需求计划需要反复导数、拼表和人工更新。

由此带来的问题：

1. 同一指标在不同人员的台账中口径不一致。
2. 当前库存、呆滞库存、预测和物料数据更新不及时。
3. 无法识别某个数值对应的数据时间及来源。
4. 关键节点发生后没有固定快照，后续无法复盘当时的决策依据。
5. 数据重复录入，耗时且容易出错。
6. 需求计划需要人工维护总台账，承担大量导数、拼表和数据核对工作。
7. 管理层查看报废金额、积压金额和超期原因时，仍需临时汇总。
8. 无法按退市类型、责任部门、品类和区域直接开展分析。

### 3.4 跨角色协同缺少责任链

EOM 涉及产品 GTM、区域 GTM、需求计划、销售、计划、PMC、采购和计委会等多个角色。当前系统主要支持发起人与计划人员确认，其他角色的任务仍在线下分配。

由此带来的问题：

1. 各节点缺少明确责任人和完成时限。
2. 任务进度依赖需求计划人工逐人询问。
3. 驳回、转交、补充材料和决策过程无法完整留痕。
4. 超期后没有自动预警和升级机制。
5. 人员变动或交接时容易丢失上下文。
6. 销售、计划、PMC 和采购没有统一任务清单，不清楚当前节点的完成要求及上下游依赖。
7. 需求计划需要通过群聊、私聊反复催办，无法集中识别即将超期的 SKU。

### 3.5 清库方案和 Last Buy 缺少结构化管理

当前 EOM 方案主要通过 Excel 附件上传，清库方式、Last Buy 数量、执行时间、库存处理、物料处理和费用归属无法直接查询与统计。

由此带来的问题：

1. 方案内容不可检索、不可汇总。
2. 方案变更后无法清晰对比不同版本。
3. Last Buy 计划与实际下单、生产、入库状态脱节。
4. 已批准的 Last Buy 与普通采购下单无法清晰区分。
5. 报废、改制、转卖等处理结果缺少闭环记录。
6. 销售缺少统一的预测刷新和可接受 Last Buy 数量提交入口，不清楚当前清库目标及截止时间。
7. 清库方案变化主要依赖人工通知，各执行角色容易使用错误版本。
8. 计划、PMC 和采购无法在同一位置查看核料、Last Buy 及物料处置要求。

### 3.6 异常场景缺少处理机制

实际执行中可能出现新品延期、老品提前断货、新品已上市但老品积压、BOM 禁用后需追加 Last Buy、数据刷新失败等异常。当前系统没有独立的异常记录和处置流程。

由此带来的问题：

1. 异常处理依赖临时群聊和人工协调。
2. 追加 Last Buy 可能通过撤回或重新发起替代，审计链不完整。
3. 调整后的方案和责任人未形成版本记录。
4. 管理层无法快速识别影响上市切换和库存损失的重点风险。
5. 新品上市时间变化后，销售和 GTM 难以及时判断老品断货或积压风险。
6. BOM 禁用后追加 Last Buy 缺少规范的反 EOM 流程，计划、PMC 和采购无法受控协同。

### 3.7 EOL 闭环缺少统一判定

当前系统没有以成品库存、专用物料、Last Buy、在途订单及反 EOM 状态共同判断 EOL。

由此带来的问题：

1. 产品状态可能已结束，但仍有库存或专用料未处理。
2. 不同人员对“已完成 EOL”的理解不一致。
3. 需要人工核对多个系统后才能关闭产品。
4. 无法提供可靠的 EOM 周期、清库达成率和物料关闭率。
5. 需求计划无法通过系统直接确认闭环条件是否全部满足。
6. 管理层无法获得可信的整体进度、关键风险和最终闭环结果。

### 3.8 现有数据能力没有形成业务闭环

系统已具备部分核料、库存、销量、BOM 和物料测算能力，但这些数据没有统一汇聚到 EOM 工单及产品台账中。

由此带来的问题：

1. 已建设的数据能力未充分转化为用户价值。
2. 用户仍需在线下重复维护系统已有数据。
3. 数据计算结果与业务决策、任务执行之间缺少关联。
4. 计算失败或口径异常时，用户不容易及时发现。

## 四、项目目标

### 4.1 总体目标

建设以 EOM 工单为载体、以 8 位 SKU 为最小管理单元的全生命周期退市管理平台，覆盖：

退市触发 → 销售预测刷新 → 核料 → 清库及 Last Buy 方案确认 → 正式 EOM → 库存清理 → 物料清理 → 异常处置 → S&OP 复盘 → EOL 闭环。

### 4.2 具体目标

1. 将主动退市和被动退市流程在线化，并按业务类型生成对应节点。
2. 将产品、预测、库存、Last Buy、物料和清库信息集中到统一台账。
3. 将每个流程节点落实到具体责任人、截止时间和完成标准。
4. 通过任务提醒、超期预警和升级机制减少人工催办。
5. 对清库方案、Last Buy、报废决策和反 EOM 进行全过程留痕。
6. 通过统一业务条件自动判定 SKU 是否完成 EOL。
7. 为业务复盘和管理决策提供及时、准确、可追溯的数据。
8. 逐步替代线下 EOM 台账及清尾跟踪表。

## 五、项目价值

### 5.1 业务价值

1. **降低库存损失**：通过新品延期、老品断货、库存积压、呆滞库存和专用料风险预警，提前调整 Last Buy 与清库方案。
2. **提高退市效率**：从发起到 EOL 全程可视，减少节点等待和重复沟通，缩短 EOM 周期。
3. **保障新老品平稳切换**：将新品里程碑、老品库存和预测联动管理，降低断供及双库存风险。
4. **提升计划准确性**：统一预测、库存和核料数据口径，为 Last Buy 决策提供可靠依据。
5. **规范异常处置**：反 EOM、追加 Last Buy、报废和方案调整均形成正式记录，避免临时操作失控。

### 5.2 用户价值

1. 产品 GTM 能快速、完整地发起退市并持续掌握执行结果。
2. 需求计划不再依赖手工拼接台账，可将精力转向风险分析和业务推动。
3. 各责任角色通过待办明确知道“何时、为哪个产品、需要完成什么”。
4. 管理层能够直接查看进度、风险、金额和超期原因，减少临时取数。
5. 新成员或交接人员可从工单中完整了解历史过程。

### 5.3 管理价值

1. 建立统一的 EOM 流程、角色职责、数据口径和闭环标准。
2. 将线下协同转化为可监控的节点任务和 SLA。
3. 将报废、改制、转卖、Last Buy 等关键决策纳入审计链。
4. 支持按组织、品类、区域、退市原因和责任部门开展复盘。
5. 为后续优化产品组合、库存策略和新品切换机制提供数据基础。

### 5.4 系统与数据价值

1. 复用现有核料、库存、销量、BOM 和物料计算能力，减少重复建设。
2. 建立动态指标、业务事件、人工决策和主数据快照的分类管理机制。
3. 让页面、导出和复盘使用同一数据口径。
4. 通过数据来源、更新时间和历史快照提高结果可信度。
5. 形成可扩展的产品生命周期管理基础能力。

### 5.5 可衡量的预期收益

项目上线后，应持续观测以下指标：

1. 线下 EOM 台账使用率及替代率。
2. EOM 工单节点按时完成率。
3. 平均 EOM 周期及预计 EOL 达成率。
4. 清库达成率和专用料关闭率。
5. 呆滞库存数量、金额及占比变化。
6. 新品延期导致的断货或积压风险数量。
7. 人工催办次数和台账整理工时变化。
8. Last Buy 计划与实际执行偏差。
9. EOL 自动闭环率和人工复核率。

具体基准值与目标值需在上线前由业务补充确认。

## 六、用户角色与核心诉求

| 用户角色 | 核心诉求 |
| --- | --- |
| 产品 GTM | 管理新老品切换计划，发起主动退市，跟踪执行并处理异常 |
| 区域 GTM | 发起被动退市，维护区域退市原因及范围，推动区域执行 |
| 需求计划 | 统筹核料、方案、任务、预警、清尾和闭环 |
| 销售 | 刷新预测，确认可接受 Last Buy 数量，执行成品清库 |
| 计划 | 参与核料，确认生产与 Last Buy 可执行性 |
| PMC | 管理专用物料的改制、转卖、报废及关闭 |
| 采购 | 执行 Last Buy 采购，维护下单、生产、在途及入库进度 |
| 计委会 | 决策超权限报废及重大异常方案 |
| 管理层 | 查看进度、风险、库存与物料损失，开展 S&OP 复盘 |

## 七、需求范围

### 7.1 本期范围

1. EOM 工作台。
2. EOM 工单列表。
3. 主动退市和被动退市发起。
4. EOM 工单详情及流程时间轴。
5. 节点任务与责任人管理。
6. EOM 产品在线台账。
7. 清库及 Last Buy 方案管理。
8. 库存、物料和 Last Buy 执行跟踪。
9. 风险预警与异常处理。
10. 反 EOM 管理。
11. S&OP 复盘与 EOL 自动闭环。
12. 消息、待办、超期提醒和操作日志。

### 7.2 业务边界

1. GTM 系统负责 EOM 流程编排、任务协同、台账汇聚、风险预警和闭环判定。
2. 预测、库存、采购、BOM、生产、报废审批等专业业务继续在原系统执行。
3. GTM 系统展示并关联专业系统结果，不替代采购下单、MRP、库存交易及报废审批。
4. 首期不要求一次性治理全部历史主数据，但必须识别并提示影响 EOM 发起或闭环的数据缺失。

## 八、总体业务流程需求

### 8.1 主动退市

1. 产品 GTM 维护新老品切换关系及新品关键时间。
2. 替代新品满足业务发起条件后，产品 GTM 发起主动 EOM。
3. 销售刷新预测并维护可接受的 Last Buy 数量。
4. 需求计划组织计划、PMC 和采购完成核料；计划人员在核料页按 SKU 填写并确认结论，全部 SKU 确认后核料定版。
5. 相关角色共同确认清库、Last Buy、库存及物料处理方案。
6. 方案确认后 SKU 进入正式 EOM，开始执行清库。
7. 系统持续跟踪成品库存、专用物料、Last Buy 和异常风险。
8. BOM 禁用后如需追加 Last Buy，必须走反 EOM 流程。
9. 月度 S&OP 对超期及高风险事项进行复盘。
10. 满足闭环条件后，SKU 自动进入 EOL。

### 8.2 被动退市

1. 区域 GTM 根据生命周期、销量、利润、费用、MOQ、法规或供应中断等原因提报。
2. 系统记录标准退市原因；选择“其他”时必须补充说明。
3. LBU 支持月度评审及特殊事项实时发起。
4. ABU 支持月度预排查和季度统一发起。
5. 提交后依次执行预测刷新、核料、方案确认、正式 EOM、库存清理、物料清理和 EOL 闭环。
6. 被动退市不要求维护新老品切换计划，原则上不包含反 EOM 节点；确有异常时按专项异常处理。

## 九、用户功能需求

### UR-01 EOM 工作台

作为 EOM 管理人员，我希望在一个页面查看所有进行中事项和风险，以便确定当天需要优先处理的工作。

需求内容：

1. 展示进行中工单、待我处理、超期任务、风险 SKU、本月新增 EOM 和本月完成 EOL 等指标。
2. 展示清库达成率和专用料关闭率。
3. 支持按工单阶段、退市类型、责任部门和风险等级查看分布。
4. 展示预计 EOL 逾期、清库风险和呆滞库存金额较高的事项。
5. 点击指标或图表后，可进入对应筛选结果。
6. 数据需标明统计范围和更新时间。

### UR-02 EOM 工单查询

作为业务用户，我希望按产品、负责人、阶段、时间和风险快速找到工单，以便处理及跟踪。

需求内容：

1. 支持按 EOM 流水号、核料流水号、Model、SKU、退市类型、退市原因、责任人、工单阶段、产品状态、超期情况及时间范围查询。
2. 列表展示退市类型、发起人、产品范围、当前阶段、当前责任人、超期状态、预计 EOL、清库进度、专用料关闭率和方案版本。
3. 用户可从列表直接进入查看、编辑、当前节点处理、异常处理、反 EOM 和日志。
4. 支持导出当前筛选结果。
5. 列表状态必须反映真实执行阶段，计划确认后不得显示业务完结。

### UR-03 发起主动 EOM

作为产品 GTM，我希望关联新品计划并发起主动退市，以便提前安排老品清库。

需求内容：

1. 选择主动退市及适用组织范围。
2. 选择老品 Model 或 8 位 SKU。
3. 维护迭代新品 SKU、新品预计 CR 时间、新品上市时间、预计 EOL 和退市原因。
4. 系统自动带出产品基础信息及默认责任人。
5. 支持上传辅助附件及填写备注。
6. 提交后生成工单、SKU 台账和销售预测刷新任务。
7. 提交后相关 SKU 产品状态进入“准备 EOM”。

### UR-04 发起被动 EOM

作为区域 GTM，我希望依据标准退市规则提报被动退市，以便统一评审和执行。

需求内容：

1. 选择被动退市及 LBU、ABU 范围。
2. 从标准退市原因中选择一项或多项。
3. 选择“其他”时必须填写具体原因。
4. 选择产品范围并维护预计 EOL 时间。
5. 系统根据组织规则带出对应责任人和后续节点。
6. 支持批量导入 SKU，并反馈每行成功或失败原因。

### UR-05 产品范围完整性校验

### UR-06 节点任务与协同

### UR-08A 核料结论填写、页面确认与导入快录

作为计划人员，我希望在核料信息页直接改最终下单数量、金额等并按 SKU 确认（可批量勾选），导入只用于快速录入。

需求内容：

1. **现网工单「确认」只跳转核料信息详情**，不在工单列表提交确认。2.0 不得把核料确认显示为业务完结；整单阶段仍停在核料中，直到该单全部 SKU 都确认。
2. 最终下单数量、最终报废金额、原因、下单后最快交付时间（天数）为 **8 位 SKU 一份**。**计划负责人、结论为 MSKU 一份**，与现网核料表不合并这两列一致。勾选确认仍按 8 位 SKU（多 MSKU 合并成一行勾选）。
3. 「我负责某 MSKU」= 该行计划负责人 = 当前登录人。「我负责某 SKU」= 该 SKU 下至少一条 MSKU 的计划负责人是我。无计划负责人的 MSKU，核料计算完成时指定为 **计划部门负责人**；之后若主数据维护了该 MSKU/SKU 的计划负责人，系统自动刷新，不再用 leader。
4. 工单「计划确认人员」由核料行计划负责人按人去重自动带出。该 SKU 下任一 MSKU 的计划负责人可勾选确认该 SKU。
5. 同一 MSKU 若主数据出现多个计划负责人，取第一负责人；其中任一人可填写该 MSKU 结论、可参与确认该 SKU。
6. **主路径是页面直改**：数量/金额/原因按 SKU 编一次；结论按 MSKU 各编。导入只解决快速录入，写入后不自动确认。
7. 核料详情提供按 **当前工单** 导出模板和导入。一次只允许导入 **一个工单** 的数据，禁止一张表混多个 EOM。
8. 模板一行一个 MSKU。可填列：下单后最快交付时间（天）、最终下单数量、最终报废金额、原因（按 SKU 覆盖）、结论（只写该 MSKU）。计划负责人只读。导入不改建议下单和锁定。同一 SKU 有多个 MSKU 时必须填 MSKU。
9. 导出默认只出当前登录人负责的 MSKU（含 leader 兜底）；可勾选「导出本单全部」，他人行只读，导入时跳过并在结果中列出。
10. 导入只覆盖「该 MSKU 计划负责人 = 当前用户」且该 SKU 尚未确认的行。他人行跳过；单行失败不影响其他有效行。核料已定版、计算失败、草稿、或工单已过核料节点时禁止导入。
11. 枚举：结论为 `lastbuy后报废` / `不补单报废`；原因为 MOQ物料结余、销售需求变化、供应链需求外风险备料、物料报废金额小于等于2万。
12. 勾选 SKU 后点「确认所选 SKU」。该 SKU 的数量/金额/原因未填，或该 SKU 下任一 MSKU 结论为空，提醒后该 SKU 不得确认。已填齐的所选 SKU 可以确认并锁定（该 SKU 下全部 MSKU 只读）。
13. 列表展示确认进度（已确认 SKU / 本单 SKU）。确认部分 SKU 不改整单阶段。全部 SKU 确认后自动核料定版，工单进入待方案决策。
14. 整单定版后全员只读。仅整单被驳回后解锁，可再次填写、导入和确认。

### UR-09 清库及 Last Buy 方案

## 十、EOM 产品台账字段需求

### 10.1 工单与产品信息

1. 提报时间：首次正式提交 EOM 的时间。
2. Model：SKU 所属 Model。
3. SKU：8 位 SKU，作为最小退市管理单元。
4. 场景：发起时保存产品所属场景。
5. 品类：发起时保存产品所属品类。
6. 国家规格：产品适用国家或规格。
7. 渠道：按 MSKU 或销售明细展开。
8. 平台：按 MSKU 或销售明细展开。
9. 线上/线下：根据渠道属性展示。
10. 产品状态：展示当前产品生命周期状态。
11. 产品类型：展示成品、配件等业务分类。
12. 上市时间：产品首次上市日期。
13. 在售时长：根据上市时间与当前日期或实际 EOL 时间计算。

### 10.2 新品迭代与 EOM 计划

14. 是否新品迭代：标识是否存在替代新品。
15. 新品迭代 SKU：关联一个或多个替代新品 SKU。
16. 新品预计 CR 时间：展示新品当前预计关键里程碑时间。
17. 迭代新品上市时间：展示新品最新计划上市时间。
18. 发起 EOM 时间：工单正式提交时间。
19. 预计 EOL 时间：当前生效方案的目标 EOL 时间。
20. EOM 时长：未闭环时按当前日期计算，已闭环时按实际 EOL 时间计算。

### 10.3 Last Buy 信息

21. Last Buy 时间：需分别展示计划时间、实际下单时间和完成时间。
22. Last Buy 数量：展示最终确认数量，并可追溯计划与实际差异。
23. Last Buy 完成状态：展示从未发起到已完成的执行进度。
24. Last Buy 下单后总计库存：保存 Last Buy 下单事件发生后的全链路库存快照。

### 10.4 库存、销量与预测

25. 当前总计库存：展示全链路成品库存。
26. 呆滞库存：展示符合统一库龄口径的库存数量及金额。
27. 呆滞库存占比：呆滞库存占当前总库存的比例。
28. 专用料库存：展示数量和金额。
29. 通用料库存：展示数量和金额。
30. M-3 月销量：前三个自然月的销量。
31. M-2 月销量：前两个自然月的销量。
32. M-1 月销量：上一个自然月的销量。
33. 销售总预测：当前有效预测版本的总量。
34. 预计 EOL 时间前总预测：当前日期至预计 EOL 的预测合计。
35. DOS：当前可用库存可支持销售的天数；无销量时显示“无销量”。

### 10.5 清库执行

36. 清库进度：基于正式 EOM 或 Last Buy 完成后的基准库存计算。
37. 清库方案：展示当前生效的结构化方案及版本。
38. 备注：记录业务补充说明。

### 10.6 建议增加的管理字段

为满足在线协同及管理需要，台账还需增加：

1. EOM 流水号。
2. 退市类型。
3. 退市原因。
4. 当前工单阶段。
5. 当前责任人。
6. 实际 EOL 时间。
7. 是否超期。
8. 风险等级及风险类型。
9. 专用料关闭率。
10. 数据更新时间。

## 十一、核心业务规则

### 11.1 状态管理

1. EOM 工单阶段、SKU 产品状态和节点任务状态必须分别管理。
2. 工单阶段用于表示整体流程进度。
3. SKU 产品状态用于表示产品生命周期。
4. 节点任务状态用于表示责任人的执行进度。
5. 方案确认后工单进入 EOM 执行，不得直接显示完结。
6. 仅全部 SKU 完成 EOL 后，工单才可闭环。
7. 撤回仅允许「启动 EOM」；关闭仅允许「草稿、启动 EOM」，必须填写原因。核料中及之后不可撤回、关闭。
8. 撤回或关闭后，SKU 从「准备 EOM」释放回原产品状态。重新发起为原单回草稿，流水号不变，关闭原因与日志保留。
9. 方案驳回仅「待方案决策」回到核料中，整单解锁。节点任务驳回不改变工单阶段，不允许核料中退回启动 EOM。
10. 正式 EOM 后方案改版必须会签并留版本，工单阶段不退回。BOM 已禁用追加 Last Buy 走反 EOM，不走改版。
11. 产品状态含未上市；异常标识本期为已驳回、数据异常、反 EOM 中。

### 11.2 清库进度

1. 有 Last Buy 时，以 Last Buy 完成后的基准库存作为起点。
2. 无 Last Buy 时，以正式 EOM 时的基准库存作为起点。
3. 基准库存为零且当前库存也为零时，清库进度为 100%。
4. 基准库存为零但当前库存大于零时，标记基准异常，不直接计算进度。
5. 所有进度需显示计算时间。

### 11.3 DOS

1. DOS 按当前可用库存除以平均日销计算。
2. 当前可用库存是否包含在途、平均日销周期需由业务统一确认。
3. 平均日销为零时显示“无销量”，不得展示无限值。
4. DOS 的数据来源和计算时间需可查看。

### 11.4 EOL 判定

1. 成品库存和专用物料必须同时为零。
2. 不得存在未完结 Last Buy 或在途订单。
3. 不得存在执行中的反 EOM。
4. 任一条件未满足时均不得自动闭环。
5. 自动判定结果必须保留数据快照和日志。

### 11.5 方案和数据追溯

1. 主数据在发起时保存快照。
2. 库存、预测、销量、DOS 和物料作为动态数据定时刷新。
3. 发起、正式 EOM、Last Buy 下单、Last Buy 完成及实际 EOL 等关键事件保存不可变快照。
4. 退市原因、清库方案、报废决策和备注等人工决策需记录版本。
5. 所有关键数据需展示来源、口径及更新时间。

## 十二、消息和提醒需求

1. 新任务生成时通知责任人。
2. 任务到期前提醒责任人。
3. 任务超期后通知责任人和需求计划。
4. 长期超期或高风险事项按规则升级通知管理人员。
5. 节点被驳回、任务被转交、方案版本变更时通知相关人员。
6. 新品延期、清库偏低、断货、积压、呆滞库存、专用料未关闭、Last Buy 超期和数据异常时发送风险通知。
7. SKU 完成 EOL 及工单闭环时通知全流程相关角色。
8. 通知应能直接进入对应工单、任务或风险事项。

## 十三、数据权限需求

1. 用户按组织、区域、产品线和业务角色查看有权限的 EOM 数据。
2. 发起人可编辑草稿及被驳回的工单。
3. 当前责任人可处理本人任务。
4. 清库方案、Last Buy 和物料处置由对应角色维护。
5. 超权限报废决策仅对授权人员开放。
6. 需求计划及授权管理人员可查看全流程数据和风险。
7. 关键字段修改和人工闭环需具备专项权限并记录日志。

## 十四、异常与边界需求

1. 新品项目取消后，系统应支持暂停、调整或转为被动退市，具体规则待业务确认。
2. 新品延期时，应重新评估库存覆盖和 Last Buy，并形成新方案版本。
3. 老品可能提前断货时，应预警并支持发起补充方案。
4. 新品已上市但老品积压时，应支持升级清库方案。
5. BOM 禁用后追加 Last Buy 必须发起反 EOM。
6. 库存、预测、BOM 或物料数据获取失败时，应显示数据异常，不得使用错误结果自动闭环。
7. EOM 工单关闭或暂停时，应说明原因并处理未完成任务。
8. 导入 SKU 时，应逐行反馈失败原因，不因单行失败影响其他有效数据。
9. 历史数据迁移后无法还原的指标应明确标识，不得伪造历史快照。

## 十五、验收标准

### 15.1 发起与产品范围

1. 能正确区分主动退市和被动退市。
2. 按 Model 发起时能完整带出全部有效 8 位 SKU。
3. 排除 SKU 时必须填写原因。
4. 已 EOL 或已存在进行中 EOM 的 SKU 无法重复提交。
5. 批量导入能反馈逐行处理结果。
6. 提交后 SKU 自动进入“准备 EOM”。

### 15.2 流程与任务

1. 主动、被动退市按规则生成不同节点。
2. 每个节点均有责任人、截止时间和处理记录。
3. 计划人员在核料页按 SKU 确认结论后，工单不得显示业务完结；全部 SKU 确认后核料定版，进入待方案决策。方案确认后进入 EOM 执行，而非流程完结。
4. 核料结论以页面直改为主，导入仅快录；勾选单位为 8 位 SKU。计划负责人、结论按 MSKU；数量/金额/原因按 SKU。自己负责的 SKU 在全部 MSKU 结论已齐后即可确认。
5. 驳回、转交和超期处理均有完整记录。
6. 超期任务和高风险事项能够自动提醒。

### 15.3 台账与数据

1. 用户确认的台账字段均可查看和导出。
2. 动态指标展示数据来源和更新时间。
3. 关键业务事件保留不可变快照。
4. 支持按 SKU、Model、工单查看，并可展开渠道明细。
5. 页面与导出数据口径一致。
6. 计算失败不得展示为成功。
7. 库存、预测和物料数据抽样结果与源系统一致。

### 15.4 方案与 Last Buy

1. 清库方案支持结构化录入和版本追溯。
2. Last Buy 可从计划跟踪至实际入库完成。
3. Last Buy 下单及完成后自动保存库存快照。
4. EOM 下单管控不阻断已审批的 Last Buy。
5. 数量或时间偏差能够产生风险提示。

### 15.5 清尾与 EOL

1. 成品库存、专用物料、未完成 Last Buy、在途订单和反 EOM 状态共同参与闭环判断。
2. 任一条件未满足时不得完成 EOL。
3. 满足全部条件后 SKU 自动切换为 EOL。
4. 自动闭环失败可重试并支持人工复核。
5. 工单内全部 SKU 闭环后，工单才显示“EOL 已闭环”。
6. 闭环过程具有完整数据快照和操作日志。

## 十六、优先级建议

### P0：口径与入口治理

1. 确认 SKU 粒度、流程状态和 EOL 闭环规则。
2. 统一台账字段及 DOS、呆滞库存、清库进度等指标口径。
3. 补齐主动/被动退市、新品迭代和产品范围完整性校验。
4. 修正计划确认后直接完结的问题。
5. 确保核料及库存、物料计算结果可信。
6. 核料在核料页按 SKU 勾选确认，计划负责人与结论按 MSKU；导入只用于快录；全部 SKU 确认后自动定版。

### P1：在线台账与任务流

1. 建设 EOM 工单详情和产品在线台账。
2. 上线跨角色节点任务、SLA、提醒和超期升级。
3. 上线结构化清库方案及 Last Buy 跟踪。
4. 上线动态数据刷新、关键快照和操作日志。
5. 基本替代线下台账和人工催办。

### P2：执行闭环与经营管理

1. 上线库存、物料清理及风险预警。
2. 上线报废决策关联、反 EOM 和异常处置。
3. 上线 S&OP 复盘视图及经营指标。
4. 上线 EOL 自动闭环和管理看板。

## 十七、待业务确认事项

1. DOS 的可用库存是否包含在途，平均日销采用多少天。
2. 呆滞库存的库龄及库存范围。
3. Last Buy 时间是否分为计划时间、下单时间和完成时间。
4. Last Buy 下单后总计库存的准确统计时点。
5. 渠道、平台和线上/线下信息的默认展示粒度。
6. PMC、采购等责任人是否可从主数据自动匹配。
7. 计委会审批继续在现有审批系统完成，还是需在 GTM 内处理。
8. ABU 超金额事项的决策人配置方式。
9. 新品项目取消后，已发起主动 EOM 的处理规则。
10. EOM 后是否允许特批普通采购下单。
11. 专用料清零按数量、金额还是双重条件判断。
12. 历史已“完结”的 EOM 如何识别并迁移为真实清尾状态。
13. 各节点 SLA、提醒时间和超期升级层级。
14. 项目收益指标的现状基准值和上线目标值。

## 十八、需求成功标准

本项目的成功不以“新增了多少字段”或“上线了多少页面”衡量，而以实际业务是否形成闭环衡量。

上线后，对于任意一个 EOM SKU，用户应能在系统中准确回答：

1. 为什么退市。
2. 由谁发起、谁正在处理。
3. 当前处于哪个业务阶段。
4. 新品何时上市，老品预计何时 EOL。
5. Last Buy 计划和实际执行情况如何。
6. 当前还剩多少成品库存、呆滞库存和专用物料。
7. 清库进度是否符合计划。
8. 当前存在什么风险，谁负责解决。
9. 清库方案发生过哪些调整。
10. 最终何时、依据什么数据完成 EOL 闭环。
