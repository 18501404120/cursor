# H8120 协作流程 2.0 设计

> 依据：`01核心需求/核心需求.md` + `H8120协作泳道图.html`（1.0 现状）+ `方案框架.md`  
> 定位：回答「为满足知识解耦核心需求，协作流程应变成什么样」——保留现有阶段节点，改造节点之间的运转方式。

---

## 一句话结论

**阶段节点（CD→KO→ES→TL→DR→BT→CR）不变；协作从「角色串行等文档」改为「解耦组并行自转 + 汇入点汇合验收 + 平台维护机制 + 关键信息字段化」。**

---

## 1. 1.0 → 2.0：协作流程变在哪里

### 1.1 现状（1.0）在泳道图里暴露的问题

对照 H8120 协作泳道图，1.0 的典型特征是：

| 特征 | 泳道图事实 | 带来的问题 |
|---|---|---|
| **串行主链** | 结构板框 → 电子原理图 → 嵌入式固件 → Sourcing 打样 | 下游大量「等上游」；整机没起来前单系统难独立推进 |
| **PM/项目经理中枢** | KO 末项目经理收齐 PRD/BOM/图纸才出计划表与 KO 报告 | 汇合责任压在统筹岗，而非各块自主 + 到点验收 |
| **文档 I/O** | 卡片写「入/出」为文档名（PRD、板框图、试产报告…） | 信息散落文件夹；版本、状态、结论不可检索 |
| **迭代靠人记** | 大量「可能在 CD/ES/DR 重复发生」 | 轮次、结论、谁改了什么，缺乏结构化记录 |
| **协同靠临时沟通** | 跨角色依赖线密集，无正式协同入口 | 变更影响范围靠项目经理个人经验判断 |

### 1.2 目标（2.0）协作形态

```text
                    ┌─ 平台层（PM/PD）：价值共识 · 机制 · 字段上下文 ─┐
                    │                                              │
  CD ──► KO ──► ES ──► TL ──► DR(含试产轮次) ──► BT ──► CR          │
         │      │      │      │                                        │
         │      │      │      └─ JP-DR-n（子汇合）                      │
         │      │      └─ JP-TL（开模冻结）                              │
         │      └─ JP-ES（整机可行性）                                  │
         └─ JP-KO（立项共识 + 各组认领）                                │
                                                                        │
  解耦组并行：结构 │ 制冷 │ 电控 │ 固件 │ APP │ 质量 │ 供应链 │ 认证 │ 包材 │ 制造导入
                    └──────────── 平时各组自转，到 JP 带清单汇合 ────────┘
```

**不变**：CD/KO/ES/TL/DR/BT/CR 阶段节点名称与评审意义；GTM 的 GR 挂接节奏。  
**要变**：节点之间各块并行；汇入点写清「带什么、过不过」；PM/PD 维护机制而非催文档；协作 I/O 升级为字段状态。

## 2. 解耦组划分（需求 A）

不把项目只看成「岗位×阶段」，而是划成 **可独立策划、确认、验收** 的解耦组。H8120（制冰机家电）建议如下：

| 解耦组 | 主导 | 辅助 | 组内可独立先验什么 | 对外关键接口（字段化） |
|---|---|---|---|---|
| **G1 外观 ID** | ID | 结构 | ID/CMF、拆件可行性 | 外形尺寸、拆件方案、CMF 状态 |
| **G2 箱体结构** | 结构工程师 | ID、专利、Sourcing | 板框、3D、手板/ES 样机、2D/BOM | 板框版本、安装位、结构 BOM 版本 |
| **G3 制冷系统** | 制冷工程师 | 结构 | 制冷件图纸、单系统调试（冰量等） | 制冷方案版本、关键件规格、ES 调试结论 |
| **G4 电控硬件** | 电子工程师 | 结构 | 原理图、Layout、PCBA | 原理图版本、板框依赖状态、电子 BOM |
| **G5 嵌入式固件** | 嵌入式软件工程师 | 电子、嵌入式测试 | 固件版本、单元测试 | 固件版本、硬件依赖版本、受控状态 |
| **G6 APP 软件** | 软件产品经理 | PM | 软件原型、纯软件子项目 | APP 原型版本、与硬件接口字段 |
| **G7 质量验证** | DQE + 测试工程师 | 各研发组 | 规格书、用例、测试报告 | 规格版本、用例覆盖率、测试结论 |
| **G8 供应链** | Sourcing | 结构、电子、制冷 | 打样、模具、物料承认 | 样品状态、模具进度、承认书状态 |
| **G9 认证合规** | 认证 + 专利工程师 | 电子、结构 | 费用评估、安规、证书 | 认证进度、风险等级、证书状态 |
| **G10 包材** | 包装工程师 | PM | 包装 BOM、受控图纸 | 包材版本、核价状态 |
| **G11 制造导入** | NPI | 结构、电子 | 工艺要求、试产总结、工业成熟度 | 工艺版本、试产轮次结论 |
| **G0 平台** | PM + 产品经理 + 项目经理 | 全体 | 价值共识、机制运转、汇入组织 | PRD 版本、JP 状态、变更日志、风险看板 |

> **接口原则**：组间不再传「等结构发我包」，而是传 **明确字段**（如 `板框版本≥v2.1`）。字段进入项目上下文字段表，变更走协同规则（见第 4 节）。

## 3. 汇入点设计（需求 A + C）

汇入点（JP）**优先对齐现有阶段节点**，DR 内设试产子汇合。每个 JP 只回答四件事：**谁到场 · 带什么 · 过/不过 · 不过怎么办**。

### 3.1 阶段节点与 JP 对照

| 阶段节点 | JP 名称 | 须到场解耦组 | 核心汇合议题 |
|---|---|---|---|
| **CD** | JP-CD | G0、G1、G2 | 概念与拆件方向；ID/结构闭环 |
| **KO** | JP-KO | G0～G11 各组代表 | 立项共识：各组认领接口、自策划资源、确认 PRD 字段 |
| **ES** | JP-ES | G2～G7、G9 | 各块预验后整机可行性；PRD 是否需调整 |
| **TL** | JP-TL | G2、G8 | 结构开模冻结；模具合同与计划 |
| **DR** | JP-DR-n | G2～G11（按轮次） | 试产第 n 轮汇合；问题关闭与设计释放 |
| **BT** | JP-BT | G0、G7 | 用户测试结论；能否进 CR |
| **CR** | JP-CR | G0、G8、G10、G11 | 转量：承认书、工业成熟度、首单信息 |

GTM 评审（GR1/GR2/GR3…）与 JP **并行挂接**，不替代研发 JP；商业锁定节奏在 ES/TL/DR/BT 与研发汇合同步考虑。

### 3.2 各 JP 汇合清单（H8120 示例）

#### JP-KO（对齐 KO 阶段节点）

| 解耦组 | 须携带（成果 + 关键字段） | 过关标准（示例） |
|---|---|---|
| G0 平台 | PRD v1、ROI、竞品字段、各 JP 共识日 | PRD 必填字段完整；各组已认领 |
| G1 ID | ID/CMF 状态=冻结候选 | 结构拆件意见已闭环 |
| G2 结构 | 板框 v1、3D 初版、结构 BOM 草案 | 板框可供电子开孔评估 |
| G3 制冷 | 制冷方案 v1、器件清单 | 不依赖整机即可打制冷件样 |
| G4 电子 | 原理图草案（可用临时板框） | 关键器件选型完成 |
| G5 固件 | 开发计划、硬件依赖说明 | 需求确认完成（**最高优先级**） |
| G7 质量 | 质量规格书、DFMEA 初版 | 核心指标可测 |
| G9 认证 | 认证费用评估 | 无阻断性合规风险 |
| G10 包材 | 包装需求确认 | 与 ID/结构尺寸对齐 |
| G11 NPI | 工艺初步评估 | 无不可制造项 |

**与 1.0 差别**：KO 不再是项目经理「收齐所有文档才评审」，而是各组 **自带清单到场**；未达标组记 JP-KO 回退项，其他组继续并行。

#### JP-ES（对齐 ES 阶段节点）

| 解耦组 | 独立预验成果 | 汇入时字段 |
|---|---|---|
| G2 结构 | ES 样机 | `ES样机状态=可用` |
| G3 制冷 | 冰量/制冷调试数据 | `制冷ES结论=达标/待优化` |
| G4+G5 | 能点亮/跑通的电控+固件 | `电控联调状态` |
| G6 APP | 软件原型 | `APP原型版本` |
| G7 质量 | 电性能/可靠性用例与首轮报告 | `ES测试结论` |
| G9 认证 | 安规评估 | `安规评估=通过/风险` |

**整机汇合议题**：核心需求是否满足；PRD 是否升级；哪些组带条件通过。

#### JP-TL（对齐 TL 阶段节点）

- **G2 结构**：3D/2D 冻结字段 `结构冻结版本`  
- **G8 Sourcing**：模具合同、模具计划表  
- **过关**：开模前不可再改外形与关键安装位；未冻结则 TL 回退，电子/固件可继续非结构依赖工作。

#### JP-DR-n（DR 阶段内子汇合，家电 TR 并入 DR）

每轮试产是一次子 JP：

| 字段 | 说明 |
|---|---|
| `DR试产轮次` | 1、2、3… |
| `本轮试产结论` | 通过 / 带条件 / 不通过 |
| `回退组` | 如 G3 制冷 + G2 结构 |
| `可继续组` | 如 G10 包材 |

**与 1.0 差别**：试产不再等项目经理凑齐「试产通知单 + 全部报告」才开下一轮；按轮次字段记录，各组对本轮负责项独立更新状态。

#### JP-BT / JP-CR

基本沿用 H8120 协作事实，补充字段：`BT结论`、`CR释放状态`、`物料承认书齐套率`。

### 3.3 汇入点时间 = 共识截止，不是压工期

- PM/PD 维护各 JP **共识日期**，可提醒、可公示风险。  
- **不**由 PM 压缩组内个人排期；Leader 保障本角色投入，不越界推他人项目。

## 4. 自主运转机制（需求 B + C）

解耦组三项自主能力（资源策划 / 需求确认 / 独自验收）靠 **平台规则** 兜底，不靠项目经理统筹。

### 4.1 四条运转规则

| 规则 | 触发场景 | H8120 示例 | 责任 |
|---|---|---|---|
| **启动** | KO 后各组认领 | 制冷组不等 ES 整机，自行排手板与供应商 | 各组主导；G0 维护 PRD 与 JP 日历 |
| **调整** | 需求/接口重大变化 | PRD 改外观 → 结构改模 | 按分级发起（见下表） |
| **协同** | A 组向 B 组提接口诉求 | 电子要结构改开孔 | 走协同单，禁止私聊即定论 |
| **汇合** | 到达 JP | ES 整机可行性评审 | G0 组织；各组带清单；未达标记回退 |

### 4.2 调整分级（建议初版）

| 级别 | 定义 | 通知范围 | 决策 | H8120 示例 |
|---|---|---|---|---|
| **P0** | 影响全项目目标或多个 JP | 全员 + GTM | PM/PD + 主导部门 Leader | PRD 改核心规格（日产量、尺寸级） |
| **P1** | 影响 2+ 解耦组接口 | 相关组 + G0 | 相关组主导人联合 | 结构改模影响电子开孔与包材 |
| **P2** | 组内或单接口微调 | 直接相关组 | 组内自决，字段留痕 | 固件小版本修复 |

### 4.3 协同请求（组间诉求）

```text
发起（需求方组）→ 字段说明「要什么、何时需要、影响什么」
    → 响应方组确认可行性 / 排期 / 拒绝理由
        → 达不成 → 升级 P1/P0
            → 结果写入上下文字段 + 变更日志
```

**1.0 对比**：电子等结构板框，现在改为「板框字段未达 v2.1 → 自动触发协同单 + 可见阻塞」，而非项目经理私下协调。

### 4.4 进度可见与风险提示

| 约定 | 内容 |
|---|---|
| JP 前同步频率 | 距 JP-ES/TL/DR 2 周起，各组每周更新本组关键字段状态 |
| 风险上报 | 判断无法按 **共识 JP 日** 汇合时，**3 个工作日内**发起调整或协同 |
| PM 动作 | 识别关键路径与 JP 风险，更新看板；**不**细排工程师每日任务 |
| Leader 动作 | 保障本角色投入；了解是否遇阻；**不催进度、不压时间** |

### 4.5 角色重新定义

| 角色 | 1.0 | 2.0 |
|---|---|---|
| **PM / 产品经理** | 出 PRD、收反馈、改 PRD | 价值共识 + 字段上下文 + 调整/协同规则维护 |
| **项目经理** | 排计划、催材料、出 KO/DR 报告 | 汇入组织 + JP 清单 + 风险看板；报告由字段汇总生成 |
| **解耦组主导** | 按阶段交文档 | 资源策划、需求确认、独自验收、更新本组字段 |
| **部门 Leader** | 有时兼催进度 | 保投入、解资源；不推别人项目节点 |

## 5. 数字驱动：协作 I/O 字段化（需求 D）

### 5.1 原则

- 上下文 ≠ 文档库；**先字段、后附件**。  
- 协作泳道图里的「入/出」逐步升级为 **字段 + 状态 + 版本**。  
- 长篇图纸/报告仍存附件，挂在字段下。

### 5.2 从 H8120 1.0 I/O 抽取的优先字段（试点最小集）

| 类别 | 字段示例 | 原 1.0 文档对应 |
|---|---|---|
| 产品定义 | `PRD版本`、`核心规格冻结状态` | PRD、PRD 更新 |
| 结构 | `板框版本`、`结构冻结版本`、`ES样机状态` | 板框图、3D、ES 样机 |
| 制冷 | `制冷方案版本`、`制冷ES结论` | 制冷器件图纸、调试数据 |
| 电控 | `原理图版本`、`Layout版本`、`联调状态` | 原理图、Layout |
| 固件 | `固件版本`、`受控状态` | 固件、受控固件 |
| 质量 | `DFMEA版本`、`ES测试结论`、`DR试产轮次` | DFMEA、测试报告 |
| 供应链 | `模具进度`、`样品状态`、`承认书齐套率` | 模具计划、承认书 |
| 认证 | `认证进度`、`专利风险等级` | 认证报告、专利评估 |
| 汇入 | `JP-KO状态`、`JP-ES状态`… | KO 报告、评审结论 |
| 变更 | `最近变更级别`、`变更摘要` | 会议纪要、邮件 |

### 5.3 呈现形态

```text
项目详情页
├── 摘要区：上表关键字段（按角色过滤视图）
├── 下钻：组内明细字段 + 附件
└── 变更日志：P0/P1/P2 + 协同单记录
```

**落地节奏**：先用 Excel/轻量页面跑通 H8120 字段集，再渐进系统化的项目详情页。

## 6. 阶段协作主线（2.0 时序）

以 H8120 主链为例，说明 **同一阶段节点内** 2.0 如何跑。

### 6.1 CD → KO

```text
CD：G1↔G2 迭代 ID/拆件（保留 1.0 事实，字段记录轮次）
     G0 输出价值共识 + 初始化上下文字段表
KO前：各组读 PRD 字段 → 完成需求确认（组内最高优先级）
JP-KO：各组并行认领 → 汇合出立项结论（非收齐文档式）
```

### 6.2 KO → ES（并行收益最大的区段）

```text
并行自转：
  G2 结构手板/ES样机  │  G3 制冷单系统调试  │  G4/G5 电控联调
  G6 APP 原型         │  G7 测试用例准备    │  G9 认证评估
  G10 包材方案        │  G8 打样/寻源

协同：接口字段未达标 → 协同单（如 G4 等 G2 板框版本）
JP-ES：整机可行性汇合 → PRD 字段是否升级
```

**对比 1.0**：制冷、APP、质量用例不再等「结构 ES 样机整机」才启动；有接口字段即可开工。

### 6.3 ES → TL → DR

```text
JP-TL：G2 冻结 + G8 开模
DR 内：
  JP-DR-1 → 问题清单字段化 → 相关组回退
  JP-DR-2 → …
  最终 JP-DR-释放：设计释放字段齐套
```

### 6.4 DR → BT → CR

BT/CR 沿用 1.0 协作链，增加字段汇总生成 CR 包，减少项目经理手工凑材料。

## 7. 与核心需求对照

| 核心需求 | 2.0 协作流程中的落点 |
|---|---|
| **A 解耦与汇入点** | 第 2 节解耦组 + 第 3 节 JP 清单 |
| **B 三项自主** | 第 4.1 启动规则；各组自带 JP 清单；组内验收 |
| **C 自主机制** | 第 4 节调整/协同/汇合/进度/同步 |
| **D 字段化** | 第 5 节；泳道图 2.0 卡片展示字段态 |
| **E 试点沉淀** | H8120 为样板；产出 JP 清单 + 机制规则 + 字段模板 |

## 8. 成功标准（协作流程视角）

1. KO 后各解耦组可 **不依赖整机** 推进至少一项独立预验。  
2. 任一 JP 可在 5 分钟内从字段摘要判断「能不能过」。  
3. 跨组阻塞走协同单，**不默认等项目经理协调**。  
4. 试产多轮有 `DR试产轮次` 字段，回退组明确，其他组可继续。  
5. 例会内容从「催文档」转为「过机制、过字段、过 JP 结论」。
