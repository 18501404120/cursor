# 研发知识解耦 —— 核心需求

> 依据：老大框架《3.机制》（1.0→2.0）+ 2026-07-30《研发解耦项目进度与自主机制设计讨论》+《新型协作模式探索》  
> 定位：本文件只回答「当前试点阶段到底要做成什么」，不展开具体方案细节。  
> 当前口径：先在 **PD 项目中验证第二种协作方式**，与现有 1.0 流程共存；长期是否全面转向 2.0，取决于试点结论。

---

## 一句话结论

在不直接替换现有 1.0 研发流程的前提下，选择合适的 **PD 试点项目**，验证一套以 **解耦主责人自主 + 组织能力供给 + 机制协同 + 数字上下文** 为核心的第二种协作方式：让可独立验证的业务单元先自主推进，在必要的汇入点（JP）汇合验收；项目经理/产品经理从「细排计划、催节点」转为「维护机制、共识与上下文的平台角色」。

---

## 1. 要解决的根本问题

| 现状（1.0） | 要突破的点 |
| --- | --- |
| 项目以主线计划、节点交付、文档流转为主 | 在复杂项目中，让可独立验证的单元先自主推进，而不是全部绑在整机主线上等待 |
| 项目经理/项目负责人是资源、决策、协调中心 | 把部分协调能力下放给解耦主责人，PM/PD 维护机制与共识，而不是包办每个细节 |
| 信息散落在 IM、邮件、文件夹、Word/Excel/PPT 中 | 把关键上下文沉淀成可检索、可更新、可复用的字段与状态，而不是继续堆文档 |
| 新元器件、新工艺、新模块常到整机汇合后才暴露问题 | 让元器件、系统模块或关键工作单元提前获得输入、资源和验证条件，尽早关闭不确定性 |
| 个人按流程被动接任务 | 让主责人主动确认需求、策划资源、安排节奏、提出诉求、完成专业验收 |

**方向**：当前不是直接废掉 1.0，而是在 PD 项目中验证一种新的协作方式是否更有利于个人自主、组织能力沉淀和研发信息数字化。

---

## 2. 目标形态：1.0 与 2.0 共存下的 PD 试点

### 2.1 1.0 —— 目标导向（现状对照）

- 逻辑：流程驱动，按 CD/KO/ES/TL/DR/BT/CR 等阶段节点推进。
- 项目负责人角色：统筹资源、决策、协调与节点推进。
- 驱动方式：文档驱动，信息散落在即时通讯、会议纪要和各类文档中。
- 适用范围：仍适用于明确、稳定、常规的项目；不会在本试点阶段被直接取消。

### 2.2 2.0 —— 第二种协作方式（当前试点要验证的形态）

- 逻辑：共识驱动 + 机制驱动，不以项目经理压缩个人工期为核心。
- 组织形态：围绕可独立验证的业务单元设置 **解耦主责人**，主责人带辅助角色和所需组织能力自主推进。
- 运作主线：**解耦 → 资源策划 → 自主推进 → 调整/协同 → 汇入验收 → 经验沉淀**。
- 汇入方式：在必要的 **汇入点（JP）** 做阶段性整体验收；JP 可复用现有阶段节点，也可按业务需要自定义。
- 驱动方式：轻量字段化先行，用字段清单、Excel 或简单页面验证关键上下文，不等待完整研发平台上线。

### 2.3 术语约定

| 术语 | 含义 |
| --- | --- |
| **1.0 流程** | 现有研发主流程，如 CD、KO、ES、TL、DR、BT、CR 等阶段节点 |
| **2.0 协作方式** | 以解耦主责人自主、组织能力供给、机制协同和数字上下文为核心的第二种协作方式 |
| **解耦单元** | 可被独立推进、独立验证、独立汇入的业务单元，可以是元器件、系统模块、关键工作包或跨角色组合 |
| **解耦主责人** | 对某个解耦单元的目标确认、资源策划、节奏安排、协同诉求和专业验收负责的人 |
| **辅助角色** | 围绕解耦主责人参与协作的结构、电子、嵌入式、光学、测试、供应链、品质等角色 |
| **组织能力** | 为主责人自主工作提供支撑的验证设备、测试平台、标准库、参数库、专家资源、供应商资源等 |
| **汇入点（JP）** | 解耦单元到点汇合验收的关口；可对齐现有阶段节点，也可按业务完整性和跨组依赖自定义 |
| **GTM 评审（GR）** | 上市侧评审，与研发节点并行挂接；自定义 JP 不能忽略商业判定、目标、开售时间等 GTM 锁定要求 |

## 3. 核心需求清单（要做成的事）

### 需求 A：解耦单元识别与汇入点设计

#### A 要做什么

1. 在 PD 试点项目中识别可解耦的业务单元，优先关注新元器件、新工艺、新系统模块和对整机风险影响大的关键工作。
2. 每个解耦单元必须明确：主责人、辅助角色、输入条件、输出成果、独立验证方式、汇入关系。
3. 设计 JP：写清汇入条件、时间共识、验收口径、参与角色、不过时的回退策略，以及其他组是否可以继续。
4. JP 不强制一一对应 CD/KO/ES/TL/DR/BT/CR；可以复用现有阶段节点，也可以按业务需要自定义。
5. 对涉及上市节奏的 JP，必须同步检查 GTM 约束，如 ES 商业判定、TL～DR 新品目标、TL 附近开售时间锁定等。

#### 会议对齐的落地点

- 解耦不等于少开会，也不等于把原流程换名字；关键是能不能拆出可独立推进、独立验证、独立汇入的单元。
- 对元器件类问题，要验证是否能在整机汇合前先搭建测试条件并关闭主要风险。
- 对结构、电子、光学、嵌入式等工作类问题，要验证能否通过更清晰的输入条件和上下文，让下游提前启动。
- 试点项目要覆盖不同类型，避免只在一个容易解耦的项目上得出片面结论。

---

### 需求 B：解耦主责人授权与自主能力

#### B 要做什么

解耦主责人要真正自主，必须拥有清晰责任和基本授权：

| # | 能力 | 含义 | 关键度 |
| --- | --- | --- | --- |
| 1 | **需求确认** | 主责人先确认目标、边界、验收口径和关键输入；确认不清不开干 | **最高** |
| 2 | **资源策划** | 主动提出所需设备、样件、供应商、测试平台、辅助角色等资源 | 高 |
| 3 | **节奏安排** | 在汇入点共识下，自主安排内部计划和推进路径，而不是由 PM 细排每日任务 | 高 |
| 4 | **协同发起** | 当需要其他组支持、决策或调整时，按机制主动提出诉求 | 高 |
| 5 | **独自验收** | 对本单元具备专业级独立验收能力，能说明过、不过和带条件通过的依据 | 高 |

#### 角色边界

- PM/PD 不再替主责人细排工作计划，也不以压缩个人工期为主要手段。
- 主责人不是只做技术执行，而是对本解耦单元的目标、资源、过程、风险、验收负责。
- Leader 要保证本角色有人投入、了解是否遇阻、必要时提醒；但不越界替项目经理催别人部门的节点。

---

### 需求 C：组织能力供给机制

#### C 要做什么

个人自主不是只靠个人意愿，必须有组织能力支撑。试点阶段要验证：

1. 主责人能否清楚提出自己需要什么组织能力。
2. 项目能否提供或协调相应能力，如验证设备、测试资源、标准件库、元器件参数库、供应商支持、专家评审等。
3. 组织能力是否能被沉淀为可复用资产，而不是每个项目临时找人、临时搭环境。
4. 当组织能力缺口影响推进时，如何提出、谁响应、多久反馈、是否影响 JP。
5. 哪些能力适合先用清单、Excel 或临时目录承载，哪些需要后续进入研发平台。

#### 要验证的问题

- 解耦主责人获得足够上下文和组织能力后，是否能更自主地推进。
- 组织能力供给是否减少等待、反复沟通和整机后置暴露风险。
- 哪些能力是 PD 项目长期应该建设的公共能力，而不是单项目一次性成本。

---

### 需求 D：自主运转机制（PM/PD 主责重新定义）

#### D 要做什么

由项目经理 + 产品经理设计并维护一套「平台式」规则，使各解耦单元在无强目标催逼下仍能自主运转。

机制至少覆盖：

1. **启动**
   - 每个解耦单元如何确认目标、输入条件、辅助角色、组织能力和 JP。
   - 主责人如何提交自己的推进思路和预期汇入时间。

2. **调整**
   - 某组需求发生重大变化、影响其他组时：如何发起、如何定级、如何同步。
   - 可先用 P0/P1/P2 作为试点分级示例，但最终以试跑可用为准。

3. **协同**
   - 组与组之间新诉求如何提出、如何响应、谁决策、谁知情。
   - 避免只靠临时 IM、私聊或临时拉会解决关键依赖。

4. **汇合**
   - JP 条件达成后的阶段性整体验收。
   - 不达标时谁回退、谁继续、是否重设 JP、是否影响 GTM。

5. **进度可见与风险提示**
   - 距 JP 前何种频率同步状态。
   - 出现时间风险、资源风险、技术风险时，多久内由谁发起诉求。
   - JP 时间是共识截止信息，可提醒、可共享；不是不允许延期或强制压缩时间。

6. **信息实时同步**
   - 调整、决策、验收结果进入上下文字段，相关组能及时获取。
   - 关键信息变化要有日志，避免只靠会议口头同步。

**角色变化一句话**：PM/PD 从「推研发出节点」变为「维护机制、共识、JP 和上下文的平台角色」。

---

### 需求 E：数字驱动 —— 上下文字段化原型（非文档库）

#### E 要做什么

1. 纠正错误理解：上下文 ≠「上文输出文档 / 下文输出文档」的资料库，也不是新建一个网盘。
2. 当前阶段先做轻量原型：字段清单、Excel、简单页面或手工台账均可，不等待完整研发平台。
3. 区分三类信息：
   - **决策与状态字段**：项目阶段、JP 状态、验收结论、风险等级、责任人、版本、变更日志。
   - **业务对象参数**：元器件规格、关键性能、测试条件、结构尺寸、BOM 状态、供应商信息等。
   - **原始证据资料**：PRD、图纸、测试报告、承认书、会议纪要等，作为下钻依据，不作为第一入口。
4. 先按角色调研「多数人都要看到的信息」，整理固定字段；不要求一开始把所有资料全部参数化。
5. 选已闭环历史项目（如 H8120）按 **节点 × 角色** 收集典型文档，抽取核心字段，形成第一版字段清单。
6. 先跑通再反馈：哪些字段可结构化、哪些只能保留原始资料、哪些需要后续平台能力支撑。

#### 与试点的对应

- 字段化的第一目标是支持主责人自主、组织能力调用、JP 汇入验收和跨组同步。
- 字段化不是为了立刻建设大系统，而是为了验证哪些信息真正值得进入未来研发平台。

---

### 需求 F：试点验证与经验沉淀

#### F 要做什么

1. 在真实 PD 项目上试跑解耦，必要时保留 TD/PC 等项目作为参考样本，但当前核心验证对象是 PD 第二种协作方式。
2. 历史线：用已闭环项目抽字段、看协作事实、形成字段和组织能力样本。
3. 在飞线：选择 1 个或多个在飞项目，真实按主责人自主、组织能力供给、机制规则、JP 汇入试跑。
4. 跑完一个完整解耦周期后，至少沉淀四类结果：
   - 解耦单元是怎么拆的；
   - JP 是怎么定的，是否复用现有节点；
   - 组织能力是怎么被提出、供给和复用的；
   - 项目运转机制是怎么跑的，包括调整、协同、汇合、风险提示。
5. 例会从「催进度」转为「过机制、过字段、过试点结论」；日常推进靠主责人自主 + 规则运行。

## 4. 成功标准（怎么算做成）

1. **试点定位清晰**：能够说明本项目是在验证 PD 第二种协作方式，而不是直接替换全部 1.0 流程。
2. **解耦有效**：存在可独立策划、推进、验证、汇入的解耦单元；不是简单把原有岗位工作换个名称。
3. **主责人自主成立**：主责人能自主确认需求、策划资源、安排节奏、提出诉求、完成专业验收。
4. **组织能力可供给**：试点中能识别并调用关键组织能力，并沉淀出可复用的能力清单或建设建议。
5. **机制可运转**：启动、调整、协同、汇合、风险提示有明确规则与责任边界；PM/PD 不回到细排和催逼。
6. **信息可数字驱动**：试点范围内关键上下文以字段和状态呈现为主，能按项目、角色、JP 或解耦单元检索。
7. **JP 设计可解释**：JP 可以复用现有节点，也可以自定义；能说明为什么这么设、谁来验、不过怎么办。
8. **GTM 约束不丢失**：涉及上市节奏的项目，能说明 JP 与商业判定、新品目标、开售时间之间的关系。
9. **可比较试点收益**：至少能形成前后对照，如跨组等待减少、资料查找更快、风险更早暴露、PM 手工协调减少、组织能力复用增加。
10. **可复用沉淀**：形成一套可供下一批项目参考的「解耦单元模板 + JP 模板 + 机制规则 + 字段清单 + 组织能力清单」雏形。

## 5. 明确不做 / 边界（避免跑偏）

| 不做 | 说明 |
| --- | --- |
| 不做「当前就替换全部 1.0」 | 当前是 PD 试点验证，与现有流程共存 |
| 不做「所有项目一刀切 2.0」 | 哪些项目适合新协作方式，需要试点后再判断 |
| 不做「JP 必须绑定所有阶段节点」 | JP 可复用 CD/KO/ES/TL/DR/BT/CR，也可按业务需要自定义 |
| 不做「不定目标 = 完全不管」 | Leader/机制仍要关注投入、风险和组织能力缺口 |
| 不做「把上下文做成网盘文档库」 | 目标是字段化、结构化、状态化，原始资料只是下钻证据 |
| 不做「一年半载才上线完整大系统」 | 当前先字段调研、Excel/轻量原型和机制试跑 |
| 不做「PM 继续细排、压缩每人节点」 | PM/PD 维护机制、共识和上下文，不替主责人排每日计划 |
| 不做「只证明研发周期缩短」 | 周期可能改善，但第一优先级是验证个人自主和组织能力供给 |
| 不做「未试跑就先否定变革」 | 即使最终结论不完美，也要用试点证据反馈给老板决策 |

## 8. 简述核心需求

1. **先做 PD 试点**：当前不是全面替换 1.0，而是在 PD 项目中验证第二种协作方式。
2. **拆出解耦单元**：围绕元器件、系统模块、关键工作包等对象，拆出能独立推进、独立验证、独立汇入的单元。
3. **明确主责人**：每个解耦单元要有主责人，主责人负责需求确认、资源策划、节奏安排、协同诉求和专业验收。
4. **配套组织能力**：个人自主必须有设备、测试、标准库、参数库、供应商、专家等组织能力支撑。
5. **自定义汇入点**：JP 按业务需要设计，可复用现有节点，也可自定义；重点是条件、验收、回退和继续策略清楚。
6. **PM/PD 做平台**：项目经理和产品经理维护机制、共识、JP 和上下文，不再以细排计划、催研发节点为主。
7. **上下文字段化**：先用字段清单、Excel 或轻量原型承载关键信息，不把上下文做成网盘或文档库。
8. **机制跑起来**：启动、调整、协同、汇合、风险提示都要有规则，让主责人遇到问题能按机制自主推进。
9. **兼顾 GTM**：自定义 JP 不能丢掉商业判定、新品目标、开售时间等上市侧约束。
10. **用试点说话**：最终沉淀解耦模板、JP 模板、机制规则、字段清单和组织能力清单，再判断是否扩大推广。
