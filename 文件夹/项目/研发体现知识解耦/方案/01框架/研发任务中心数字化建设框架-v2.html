数字对象：公司级任务长什么样

系统里落下来的不是节点、不是一两天的细活。组委会可同时管多个项目；每个项目各自拆约 10～20 个公司级任务。投放时先写清任务名称、任务内容、责任人，再挂 4～6 个关键项。中台方案的指标应回溯到这些字段，而不是另写一套文档。

状态机：对象一次写入，闭环后才出中台口

每条任务对象只创建一次，之后沿状态往前走。验收或汇合发现偏差时，用箭头指回「写入」，更新同一对象已挂上的字段，不把该对象拆成下一阶段。中台沉淀不是第 7 步，而是闭环之后的出口。

7

中台怎么接：任务沉淀为方案，下一款对照后再投

本章吸收历史「中台化」的四个问题和两层方案对象，全部改接到现行任务闭环。建设顺序不变：没有任务中心，中台没有输入。组委会承担原「解耦组负责人」的匹配拍板，不另起指挥链。

Q1 · 货架

已经有什么

各专业沉淀了哪些模块方案。条目要能回溯到闭环任务和验收记录。

Q2 · 匹配

新产品怎么选

组委会解耦时对照货架，每个可验收对象是复用、二次开发还是新做。

Q3 · 分流

任务中心做什么

只有二次开发和新做写成公司级开发任务。复用项只引用，不领开发任务。

Q4 · 回写

做完怎么回来

任务闭环 → 模块方案；整机汇合 → 产品方案。沉淀对象是任务，不是项目结项。

对象 A

模块方案

跨产品可引用的能力块，粒度对齐公司级任务的可验收对象（结构 / 电子 / 光学 / 嵌入式等）。

独立验收通过 → 候选；汇合后参数稳定 → 定稿。灰色候选不得当正式复用基线。

对象 B

产品方案

一款产品 / SKU 的模块组合，以及当时复用 / 改 / 新做的决策记录。

在整机级汇合后回写，不在第一条任务闭环时提前写成「这款做完了」。下一款可先打开历史组合再删改增。

三类决策如何变成是否投任务

组委会对照货架解耦投放前
复用

不投开发任务；项目汇总里记「引用方案 XX」。

二次开发

投 1 个任务；尺子写清基线方案 + 增量指标 + 验收。

新做

投 1 个任务；按量产态写完整尺子。闭环后立新方案。

沉淀规则：先有闭环任务，才有可信方案。不是每条闭环都进货架——组委会判断是否具备跨产品复用价值。中台不在任务中心内实现；任务中心也不做成货架。一期没有货架时，允许先按量产态全量当新做，但拆完就要能指出哪些对象闭环后值得沉淀。

一期观测：状态、字段完整度、验收是否就绪、变更是否登记、哪些闭环被标了可沉淀。组委会凭看板决策。
二期观测：货架能否被对照、复用 / 改 / 新做是否分流进任务、解耦参数 vs 量产参数匹配率、方案被下一款引用的次数。
