| 修订原因 | 澄清：**10 分钟是 ERP 从 BBY 等店拉订单**，不是「ERP 已知道订单后仅推 WFS 慢 10 分钟」 |

---

## 1. 先把链路说对（两段时间窗）

```text
客户在 BBY 平台下单
        │
        ▼
┌───────────────────────────────────────┐
│ 窗口 A：ERP 尚未拉单（约 ≤10 分钟）      │  ← ERP 不知道这笔单，无法锁定
│ BBY 平台侧已成交，可售仍按 ERP 上次同步展示 │
└───────────────────────────────────────┘
        │ 定时任务：从 BBY 店铺拉订单进 ERP
        ▼
┌───────────────────────────────────────┐
│ 窗口 B：ERP 已进单，尚未推 WFS 成功        │  ← 「订单锁定库存」主要覆盖这里
│ 可锁定、可扣当前可售、可参与分配池扣 L      │
└───────────────────────────────────────┘
        │ 推 WFS 仓（常与拉单同批或紧随其后）
        ▼
   WFS 实扣 / 下次拉 WFS 实查下降
```

| 窗口 | 系统是否感知 BBY 订单 | 现有「订单锁定」能否作用 | 典型风险 |
|------|----------------------|-------------------------|----------|
| **A · 拉单前** | **否**（约 10 分钟一批） | **不能** | BBY 已卖 + WM 仍按旧份额狂卖 → 超卖 |
| **B · 进 ERP～推 WFS** | **是** | **能** | 进单后至推仓前，WM 仍可能继续卖 |

**此前方案表述易误解之处**：若只写「BBY 约 10 分钟推 WFS」，容易让人以为 ERP **实时已有订单**，只是推仓慢。实际更贴切的说法是：

> **ERP 约每 10 分钟从 BBY（及 Lowes 等）拉一次订单；拉进 ERP 后再推 WFS。拉单前 ERP 无法对 BBY 新单做锁定。**

最坏情况下（拉单与推 WFS **分两档各 10 分钟**），盲区可接近 **10 + 10 分钟**；若**同一任务内拉单后立即推 WFS**，窗口 B 可压到很短，但 **窗口 A 仍存在**。

## 2. 「订单锁定库存」在纠正后的定位

| 能力 | 能解决 | 不能解决 |
|------|--------|----------|
| 进 ERP 时 +锁定、−当前 | 窗口 B；分配池算 \(P\) 时扣 \(L\) | 窗口 A（单还没进 ERP） |
| 推 WFS 成功按**实际推单件数**释放锁定 | 与 WFS 占用对齐 | 拉单前 BBY 已成交未入账部分 |
| 定时配平 + 三店回写可售 | 份额再平衡、压低子店展示 | 无法代替「更早知道 BBY 卖了什么」 |

结论：**锁定是必要但不充分**——它优化的是「ERP 已知订单之后」的承诺量，**不能单独消灭拉单间隔带来的超卖**。

## 3. 优化方向（由易到难）

### 3.0 推荐方案：上轮批量件数代理预占（待拉单预占）

> **业务假设**：无法实时拿到 BBY/Lowes 订单时，认为**下一个 10 分钟**的销量与**上一个 10 分钟**（上一批拉单/推单周期）相差不大，用**上批件数**充当窗口 A 的预占。

#### 是否合理？

| 维度 | 结论 |
|------|------|
| **总体** | **有条件合理** — 作为无 Webhook 时的 **P0 启发式**，与现有锁定、配平兼容；**不能**替代进 ERP 后的真实锁定 |
| **适用** | 拉单周期稳定（≈10min）、SKU 动销平缓、BBY/Lowes 非大促脉冲 |
| **不适用单独依赖** | 大促首发分钟、爆款上新、0→爆量、上批为 0 的冷启动 |

#### 字段设计（建议）

界面仍可用一列 **「订单锁定库存」** 对外展示，对内拆两项，避免双扣：

| 子项 | 符号 | 含义 | 何时有值 |
|------|------|------|----------|
| 待推 WFS 锁定 | \(L^{erp}_i\) | 已进 ERP、未推 WFS 成功 | 窗口 B |
| **待拉单预占** | \(L^{proxy}_i\) | 用**上批件数**估下一窗口 A | 上一批拉单/推单完成后～本批拉单前 |
| **展示/扣池合计** | \(L_i = L^{erp}_i + L^{proxy}_i\) | 参与 \(Q_{eff}=Q_{wfs}-\sum L_i-\sum S\) | 全时 |

#### 已定口径（2026-05-22 业务确认）

| 项 | 决定 |
|----|------|
| 上批件数 | **上一批「推 WFS 成功」件数**（按店、按 SKU 汇总） |
| 保守系数 \(\alpha\) | **1.0**（不放大） |
| 列表展示 | **需要拆分**：待推 WFS 锁定 + 待拉单预占 + 合计 |

```text
last_batch_qty_i = 上一批定时任务中，该店该 SKU「推 WFS 成功」件数合计
L^proxy_i := last_batch_qty_i          // α=1.0，不另乘系数
L_i       := L^erp_i + L^proxy_i     // 列表「订单锁定库存」= 合计
```

**更新节奏**（每店、每 SKU、每 10 分钟任务结束时）：

```text
1. 本批：拉单 → 进 ERP → L^erp 增加（真实锁定）
2. 本批：推 WFS 成功 → L^erp 按实际推单件数释放；记录本批推成功件数 → last_batch_qty
3. 本批结束：L^proxy_i := last_batch_qty_i
4. 下一窗口：在拉单前进 ERP 前，界面展示 L^erp（通常较小）+ L^proxy（= 上批推成功）
```

**界面列（ERP 列表建议）**：

| 列名 | 字段 |
|------|------|
| 待推 WFS 锁定 | \(L^{erp}_i\) |
| 待拉单预占 | \(L^{proxy}_i\)（Tooltip：上批推 WFS 成功 {last_batch_qty} 件） |
| 订单锁定库存 | \(L_i\) 合计 |

#### 风险与缓解

| 风险 | 缓解 |
|------|------|
| 本批爆量、下批更爆 | \(\alpha>1\)、WM 动销闸门、超卖扫描 |
| 上批为 0 | 用近 3 批 EMA，或 7 日同小时段均速；仍 0 则 \(L^{proxy}=0\) 并标记「无历史」 |
| 与 \(L^{erp}\) 双扣 | 规则：**\(L^{proxy}\) 仅覆盖尚未进 ERP 的区间**；进 ERP 后只涨 \(L^{erp}\)，不在同一笔订单上再加 proxy |
| 压低 BBY 可售、损转化 | 可售 = min(配平应有, 风控上限)；大促人工覆写 |

#### 验收要点

1. 上批拉单 25 件、本批拉单前：BBY 展示锁定 ≥25（含 proxy），\(P\) 相应减少。  
2. 本批实际拉单 22 件进 ERP：\(L^{erp}\) 反映 22，推单后释放；任务结束时 \(L^{proxy}:=22\)。  
3. 上批 0、本批突增 40：允许超卖扫描告警 + 人工/自动压可售（代理低估场景）。

### 3.1 P0 · 不改拉单频率也能做（与当前 WFS 共享方案一体）

| 序号 | 措施 | 作用窗口 | 说明 |
|------|------|----------|------|
| **0** | **上轮批量件数代理预占** \(L^{proxy}\) | **A** | **本节 3.0**；无实时订单时的核心补偿 |
| 1 | **拉单与推 WFS 同任务串联** | 缩短 B | 避免「10 分钟拉单 + 再等 10 分钟推仓」叠成 20 分钟 |
| 2 | **子店（BBY/Lowes）平台可售闸门** | 间接减 A | WM 销量激增或 Commit 接近 WFS 时，**主动压低** BBY/Lowes 回写可售（需求 02） |
| 3 | **分配池预留 / WM 缓冲** | 减 A 影响 | 可与 \(L^{proxy}\) 二选一或叠加取 max（避免重复保守需配置） |
| 4 | **超卖风险扫描（≤10min）** | A+B | Commit = 三店可售 + \(\sum L^{erp}\) + \(\sum L^{proxy}\) |
| 5 | **进 ERP 立即锁定**（已定） | B | 拉单任务一写入订单即锁，不等到推 WFS |

### 3.2 P1 · 需要平台或接口能力

| 序号 | 措施 | 前提 | 对窗口 A 的帮助 |
|------|------|------|----------------|
| 6 | **Mirakl / BBY 订单 Webhook 或消息** | 平台开放 | ERP **分钟级**进单 → 锁定提前，A 大幅缩短 |
| 7 | **平台「未发货/待履约」件数 API** | 有字段 | 扫描用「平台已售未进 ERP」估算，参与 Commit |

## 4. 推荐组合（可落地的「好方案」基线）

在**暂不改为实时拉单**的前提下，建议 **三层叠加**：

```text
第一层（窗口 A · 无实时订单）
  L^proxy := 上批拉单/推单件数（×α 可选）+ WM 动销闸门

第二层（尽量缩短 B）
  同一 cron：拉单 → L^erp 真实锁定 → 同批或下一跳推 WFS → 释放 L^erp → 刷新 L^proxy

第三层（对账与告警）
  Commit 含 L^erp + L^proxy；超卖扫描；配平与平台回写
```

有 Webhook 时：\(L^{proxy}\) 可置 0 或仅作兜底，以实时进单为准。

**预期效果**（务实表述）：

- **不能承诺 0 超卖**（窗口 A 在纯定时拉单下客观存在）。
- 可将「WM 在 BBY 单未进 ERP 期间卖光份额」的概率 **压到可运营**（大促需加第二层 P1 或人工降子店可售）。
- 与现有 **WFS 共享配平、虚拟借货、订单锁定** 兼容，无需推翻 v2 方案。

## 7. 还有没有更合理的方案？（对比与推荐）

在 **无实时拉单** 前提下，没有「又准又简单」的银弹；下表按 **实现成本 vs 防超卖效果** 排序：

| 方案 | 合理性 | 优点 | 缺点 | 建议 |
|------|--------|------|------|------|
| **A. 上批推 WFS 成功作 \(L^{proxy}\)**（**已定**） | ★★★★ | 与 10min 节奏一致、实现简单、可解释 | 大促突增会低估；上批 0 冷启动弱 | **P0 默认** |
| **B. 近 3 批推成功 EMA** | ★★★★☆ | 平滑异常单批、更稳 | 仍无实时；略滞后 | **P0+ 可选开关**，上批=0 时 fallback |
| **C. max(上批推成功, WM 近10min销量×k)** | ★★★★☆ | 抓住「WM 抢货」导致的隐性占用 | 需 WM 销量统计；k 要调参 | **与 A 叠加**（超卖扫描 / 闸门），不单替 A |
| **D. 仅压子店平台可售、不算 proxy** | ★★★ | 不改锁定模型 | 不扣分配池 \(P\)；WM 仍可能吃光逻辑份额 | 作 **辅助**，不作唯一手段 |
| **E. Webhook / 平台待履约 API** | ★★★★★ | 最接近真实 | 依赖平台 | **P1 最优**；有则 \(L^{proxy}\to 0\) |
| **F. 缩短拉单间隔（5min）** | ★★★★ | 直接缩短窗口 A | 接口与任务负载 | 运维允许时配合 A |

**推荐组合（当前阶段最优实践）**：

```text
P0：A（上批推 WFS 成功，α=1）+ 真实 L^erp + 超卖扫描 + 子店压可售
P0+：上批=0 时用 B（EMA）；WM 猛时启用 C 抬高 Commit
P1：E 替代或清零 proxy
```

**结论**：在不能改拉单频率、也没有 Webhook 时，**A 已是性价比最高的主方案**；若只选一项升级，优先 **B（EMA 兜底）** 或 **C（WM 动销联动）**，而不是换掉 A。
