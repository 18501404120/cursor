# 需求 04：商超 3P 多平台 Listing 集中维护与跨平台复用

> **来源**：`原始需求/会议1`

---

## 一、原始需求（用户表述提炼）

### 1.1 背景

- BVI 从 **Reason 迁回 Mirakl（Mysql 平台）**，需 **全部 Listing 重上**；后续还将开 **Lowes、NARS（Notes）** 等，若每个平台 **重复手工建品**，效率极低。
- Mirakl 后台 **逐条 Add Offer / Create Product**，类目多（约 **7～8 类**），**必填字段因类目而异**；CSV 导入 **仅文字**，图片用链接常 **加载失败**；**无法从 BBY 导出再导入 Lowes**。
- 产品资料（size、description 等）多在 **亚马逊或人工记忆**，ERP **无完整商超上架主数据**。
- Mirakl **店铺复制/拷店** 属付费核心能力，由 **BBY/NARS 方采购**，商超团队 **难以免费获得**。

### 1.2 需求要点

| 编号 | 原始诉求 | 会议原话要点 |
|------|----------|--------------|
| R4-1 | **跨平台 Listing 映射复用**：BBY 已上品，其他品牌/平台尽量复用 | 「BVI 已经上过的品……两个品牌是不是可以用 BVI 这边的一些？省了自己人工上传」 |
| R4-2 | **ERP 作为产品主数据源**：建一次，多平台同步 | 「库建在 ERP 上面……改完其他平台都能自动去同步」 |
| R4-3 | **补齐产品资料**：长宽高、描述、图片等进 ERP，避免反复查亚马逊 | 「size description……如果放一个 ERP 里面，我们后面好搞」 |
| R4-4 | **支持 Mirakl API 创建商品/上传**（含图片机制调研） | 「API 文档是否包含创建产品……图片传链接还是文件流」 |
| R4-5 | **按类目维护字段映射模板**，导出符合 Mirakl CSV/API | 「每种类型映射一个模板……七八个类目对应上」 |
| R4-6 | ** interim**：线下维护统一 Excel，新平台按模板导入 | 「自己维护一个表格……后面有新的平台直接往上导」 |

### 1.3 提出方关注点

- **短期**：Lowes 开店在即，先解决 **批量上架**。  
- **长期**：品牌换图、改文案后 **一处改、多店同步**（Connect 类能力在北美商超场景的等价物）。  
- **平台差异**：字段名不同（item vs name），类目必填项不同，需 **映射层** 而非简单复制。

---

## 二、问题与痛点

1. **重复劳动**：每开一店重填 100+ SKU。  
2. **数据分散**：ERP 无商超 Listing 主数据，与亚马逊资料脱节。  
3. **工具链弱**：Mirakl CSV 无图、无跨店导出；API 能力未系统评估。  
4. **付费拷店不可依赖**：需自建能力。

---

## 三、解决方案

### 3.1 分阶段路线

| 阶段 | 目标 | 做法 |
|------|------|------|
| **P0（紧急）** | Lowes 等开店上架 | ① 调研 Mirakl **按类目 CSV 模板** + 试导 1 个 SKU 多的类目；② 业务整理 **主数据 Excel**（从 BBY 导出维护记录 + 补图链接到 OSS）；③ ERP 按模板 **生成 CSV** 供导入 |
| **P1** | ERP 主数据 | 建 **商超 Listing 主数据** 模块：SKU、类目、通用属性、类目扩展属性、图片 URL（企业 OSS/CDN） |
| **P2** | API 同步 | 若 Mirakl API 支持 **Create Product / Offer + 图片**，ERP → Mirakl 自动创建；按店铺/品牌 **映射发布** |
| **P3** | 跨店复用 | 主数据 + 「已发布店铺」矩阵；新店勾选复制，经 **字段映射配置** 生成目标店数据 |

### 3.2 系统方案（ERP）

1. **主数据模型**  
   - 核心：生产 SKU / MSKU、标题、描述、长宽高重量、品牌、型号、认证等。  
   - 扩展：**类目 ID → 动态属性集**（与 Mirakl 类目模板对齐）。  
   - 媒体：主图、副图、A+（PP）图 **统一存 OSS**，对外 HTTPS 链接。

2. **映射配置**  
   - 表：`平台 + 类目 → Mirakl 字段名 / 必填 / 默认值 / 转换规则`。  
   - 支持 **BBY ↔ Lowes ↔ NARS** 同构字段复用，异构字段人工映射一次。

3. **发布流水线**  
   - 草稿 → 校验必填 → 生成 CSV 或调 API → 回写 **发布状态/错误日志**。  
   - 增量：主数据变更触发 **待同步店铺** 队列（可人工确认后批量推）。

4. **与 Mirakl 分工**  
   - 先由技术 **核对 API 文档**（创建商品、改 offer、图片上传方式）。  
   - 平台侧 **Miracle 拷店** 仅作商务备选，不作为技术主路径。

### 3.3 业务 interim（无开发或开发前）

- 按 Mirakl 下载的 **空白/导出模板** 维护 **企业级 SKU 主表**（含稳定图片 URL）。  
- 新平台：**选类目 → 填映射表 → 导出 CSV → Mirakl 导入**；图片问题统一走 **公网可访问 URL** 规范。

### 3.4 待澄清项

1. 各平台 **类目树** 与 BBY 已维护类目对照表。  
2. 图片存储：**OSS 目录规范**、是否已有亚马逊图可批量迁。  
3. Lowes 开店 **deadline** 与 P0 范围（仅导入 vs 必须 API）。  
4. 品牌方 **改价改文案权限** 是否允许 ERP 单向覆盖 Mirakl。

### 3.5 验收要点（建议）

1. P0：指定类目 **≥N 个 SKU** 通过 CSV/API 成功上架 Lowes（或目标店），图片正常展示。  
2. P1：同一 SKU 在 ERP 维护后，可 **生成 BBY 与 Lowes 两份** 合规导入文件。  
3. P2：ERP 修改标题/主图后，可 **勾选店铺批量同步**（以 API 实际能力为准）。  
4. 发布失败有 **行级错误原因** 可导出。

---

## 四、风险与依赖

- **Mirakl API 限制**：可能仅支持部分类目或仅 offer 层更新。  
- **类目必填项变更**：映射需版本化。  
- **与促销/价格需求分离**：本需求不含改价（见需求 06、07）。  
- **人力**：首期 100+ SKU 历史资料 **回填** 工作量大，需业务投入。
